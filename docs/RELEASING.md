# Releasing

A release is a GitHub release holding the `.deb`, `SHA256SUMS`, and `SHA256SUMS.sig`, cut with `tools/release` on the development host. The signing key is Sunstone's own, `~/.config/sunstone-release/release_ed25519` beside vakr's: passphrase-protected, never copied to GitHub or CI. `packaging/release-signers` lists its public half, which every package ships for self-update to check against; its fingerprint is `SHA256:8WUCE9gHrarTMP6hv8LpAeTHv04rWlzWYLNuxC3Q1Lk`.

1. **Update every component and dependency to its latest release.** `make outdated` lists the Python and npm packages with newer releases: update them (`uv lock --upgrade` in `backend/`; `npm install <package>@<latest>` in `frontend/`, since `package.json` pins exact versions). Check by hand Python (`uv python list`), Node.js (`frontend/.node-version` and the builder image in `packaging/Dockerfile`), and the builder's uv, nfpm, and Ubuntu base image. Then run `make test` and the browser tests. Latest means the newest production release of the newest release line, never a beta or pre-release: for Node.js the current line (26), not only the LTS one, since security fixes usually land on the newest line first and are back-ported later. Hold a component back at its known-good version only when the new one fails tests and there is no simple fix; say so under **Additional Notes**, naming the version held, the one that failed, and why, and try again when its next version is published.
2. Set `VERSION` (`MAJOR.MINOR.PATCH`, or `-rc.N` for a release candidate) and write its section in `CHANGELOG.md`, in this order:
   - One to three sentences summing up the release.
   - `### New`, `### Changed`, `### Fixed`, and `### Additional Notes`, each only when something goes under it: a release with a single fix has **Fixed** alone.
   - `### Lines of Code`, then `### Versions`: paste what `make release-tables` prints, run on the final tree. Lines of code are counted with `cloc` over the files git tracks that are Sunstone's own, by area, without dependencies, anything vendored, or generated files (lockfiles, `openapi.json`, `schema.d.ts`, `packaging/build-constraints.txt`, `data/sample`), and a sentence under the table says so. Versions are what the build installs, from the lockfiles, `frontend/.node-version`, `packaging/Dockerfile`, and the backend's Python: Python and the prominent components and tools. With an earlier section's Versions table in the changelog, the table has its versions as **Old** and this release's as **New**, each new version in bold where it changed.
3. Merge to `main` and push. CI must pass for that commit.
4. `make release-dry-run` runs every step except tag, push, and publish: the checks, `make deb`, `SHA256SUMS`, and the signature, verified against `packaging/release-signers`. It writes the notes to `dist/release/v<version>/release-notes.txt` and says which versions they cover, so they can be read before tagging.
5. `uv run tools/release/release.py`, run from the repository root, does it for real, asking for the key's passphrase: it tags `v<version>`, pushes the tag, and creates the release with the changelog's notes, marked as a normal release, release candidates included, so anyone can download and test it. It needs an authenticated `gh`.

**Notes that catch up.** The notes are the version's own changelog section. When versions between the last release tagged on GitHub and this one were never released, their sections come along, newest first, each under its own heading, after a line naming them: 0.6.0's notes carry 0.5.0, 0.4.0, and 0.3.0, since the last release was 0.2.0. Operators so read everything that changed since the release they have. With nothing skipped, the notes are the one section, as before. Sunstone's copy of the release tool differs from vakr's here; vakr's takes the one section only.

**Notes at full width.** GitHub shows every line break in a release's notes, so the changelog's lines, wrapped at 80 columns, would read as a narrow column. The release tool joins the wrapped lines of each paragraph and list item before publishing, leaving headings, tables, and fenced code as they are, so the notes take the page's full width. vakr's copy does not do this yet.

`make deb` builds a package from the work tree in a clean `ubuntu:26.04` container. Test builds, with `VERSION_OVERRIDE` (and `RELEASE_SIGNERS` to trust a test key), are for `make package-test` only; the release tool refuses them. To rotate the key, add the new one to `packaging/release-signers`, release that signed with the old key, and remove the old key in a later release.
