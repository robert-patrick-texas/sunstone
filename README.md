# Sunstone

**Sunstone** — Network mapping and visualization tool

Sunstone shows network operations staff a map of the network they can pan, zoom, and switch between views of: a geographic map with sites and links, a top-down hierarchy, automatic topology layouts of the whole network or of the neighborhood around a device, and a logical view of the named networks layered over the links, without geography.

> **Status:** workshop prototype. It runs on a generated mock topology and simulated live state, and has no integrations yet.

## Running it

Requires [uv](https://docs.astral.sh/uv/) and Node.js 24.

```console
$ make setup
$ make serve                                    # http://127.0.0.1:8000, small sample
$ make serve TOPOLOGY=data/sample/large.yaml    # about 3,000 devices
```

For development, run `make dev-api` and `make dev-web` in two terminals and open http://127.0.0.1:5173. `make help` lists the other tasks.

**Dev instance.** `make dev-up` runs the working tree in a container (`tools/dev-instance/`), on 127.0.0.1:8000, for checking work in progress without a release:
- The API restarts when its code or the topology file changes.
- The web UI is rebuilt once its source has been still for 3 seconds, so a change shows on reload about 13 seconds after the last save (measured). A build that fails leaves the last good one, and `make dev-logs` shows why.
- It shows the layered sample; `SUNSTONE_DEV_TOPOLOGY=data/sample/large.yaml make dev-up` shows another.
- It mounts the tree read-only and keeps its saved state in a Docker volume. `make dev-down` stops it and keeps the state; `docker compose -f tools/dev-instance/compose.yaml down -v` deletes the state too. It restarts with Docker, so it comes back after a reboot.
- It holds port 8000, so stop it before `make serve` or `make dev-api`.
- `tools/dev-instance/nginx.conf` serves it at `/sunstone/` on an existing nginx site, behind a password in `/etc/nginx/sunstone-dev.htpasswd` (written with `openssl passwd -6`), as https://dev.16k.net/sunstone/ is.

Sunstone has no sign-in: anyone who can reach it can save and delete layouts, plan and delete maintenance, acknowledge and page problems, cover shifts, and fix the documentation, under whatever name they type. It listens on 127.0.0.1 by default; give `sunstone serve` `--host`, or set `host` in its settings file, only on a network you trust.

`sunstone serve` takes the topology and where saved files go on the command line (`--topology`, `--oncall`, `--state-dir`, and one option per kind of saved file), or from a settings file with `--config`; the command line wins. `sunstone check` loads everything as the server would and says what it found or what is wrong, and `sunstone --version` says which release this is.

## Installing

Sunstone ships as one `.deb` for Ubuntu 26.04 LTS on amd64, built the way vakr's is. It is self-contained: it brings its own Python 3.15 and a locked virtual environment under `/opt/sunstone`, so the host's Python and its upgrades do not affect it. Each release at <https://github.com/robert-patrick-texas/sunstone/releases> has the package, `SHA256SUMS`, and its signature, `SHA256SUMS.sig`.

```sh
repo=robert-patrick-texas/sunstone
version=0.1.0                                             # the release to install
debver=$(printf '%s\n' "$version" | sed 's/-rc\./~rc./')    # the package's form: 0.2.0~rc.1
base=https://github.com/$repo/releases/download/v$version
curl -fL -O "$base/sunstone_${debver}_amd64.deb" -O "$base/SHA256SUMS" -O "$base/SHA256SUMS.sig"
curl -fLO "https://raw.githubusercontent.com/$repo/v$version/packaging/release-signers"
grep -v '^#' release-signers | awk 'NF {print $3, $4}' | ssh-keygen -lf -
ssh-keygen -Y verify -f release-signers -I sunstone-release -n sunstone-release \
    -s SHA256SUMS.sig < SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
sudo apt install ./sunstone_${debver}_amd64.deb
```

The first `ssh-keygen` must print the release key's fingerprint, `SHA256:8WUCE9gHrarTMP6hv8LpAeTHv04rWlzWYLNuxC3Q1Lk`; the second, `Good "sunstone-release" signature`; and `sha256sum`, `OK` for the package. If any of them does not, do not install. `apt` brings `ca-certificates`, `openssh-client` (whose `ssh-keygen` checks later releases), `systemd`, and `tzdata`.

Nothing starts on installation. The package puts the small sample network and its on-call directory in `/etc/sunstone` when there is no topology there yet, so the service has something to show. To start it:

```sh
sudo sunstone check                       # loads everything as the service would
sudo systemctl enable --now sunstone      # http://127.0.0.1:8000 on this host
```

To show your own network, replace `topology.yaml` and `oncall.yaml`, run `sudo sunstone check`, and `sudo systemctl restart sunstone`. An on-call directory that names sites the topology lacks stops the service, and `sunstone check` says which. `/etc/sunstone/config.toml` holds the same choices as the command line: `topology`, `oncall`, `state_dir`, `host`, `port`, and under `[update]`, the `repository` releases come from, `hold_version`, `https_proxy`, `tls_strict_x509`, and `api` (see Updating). The service listens on 127.0.0.1:8000 for a reverse proxy in front, which may serve it at a site's root or under a path such as `/sunstone/`; `host = "0.0.0.0"` serves everyone who can reach the port, which, without sign-in, only suits a network you trust.

**Updating.** `sunstone self-update` installs a newer signed release in place:

| Command | What it does |
|---|---|
| `sudo sunstone self-update --check` | Says whether a newer release exists, and changes nothing. It reads the settings, so it needs `sudo` or membership of the `sunstone` group, but not root. |
| `sudo sunstone self-update` | Installs the newest release if it is newer than this one, after asking. `--yes` does not ask; without a terminal and without `--yes`, nothing is installed. |
| `sudo sunstone self-update --version 0.2.0` | Installs that release, even if it is older or the same. |
| `sudo sunstone self-update --file sunstone_0.2.0_amd64.deb --sums SHA256SUMS --sig SHA256SUMS.sig` | Installs a release copied by hand to a host without GitHub access. |
| `sudo sunstone self-update --rollback` | Goes back to the version the last update came from, with the configuration and state as they were before that update; today's are saved first. |

An update:

1. Lists the 30 newest releases on GitHub, release candidates included, and takes the newest one newer than the installed version and no newer than `hold_version`, if that is set; or the one asked for, whatever the hold.
2. Downloads its package, `SHA256SUMS`, and `SHA256SUMS.sig` into `/var/lib/sunstone/update/cache/<version>/`, then checks the signature against the keys the installed package trusts, and the package against its checksum. If either check fails, nothing changes.
3. Makes sure a verified package of the installed version is at hand to roll back to, downloading it if need be.
4. Backs up `/etc/sunstone` and the state directory to `/var/lib/sunstone/update/backups/`, mode 0600, keeping five.
5. Installs the package with `apt-get`, whose `postinst` restarts the service if it was running.
6. Runs the new version's `sunstone check`, and, if the service was running, waits up to 90 s for it to answer as the new version at `/api/version`.
7. If installing or checking fails, reinstalls the previous version, restores the backup, restarts the service, and says whether it answers again.

It exits 0 when it updated or found nothing newer; 1 when a release was refused, the update was declined or failed and was rolled back, or GitHub could not be reached; and 2 for a usage error. The last result is in `/var/lib/sunstone/update/last-update.json`; the installed version, the one it replaced, and the newest other stay cached, so a rollback has a package to go back to even after a downgrade.

| Command | What happens |
|---|---|
**The daily timer.** `sudo systemctl enable --now sunstone-update.timer` updates every day, at a random moment in the four hours after midnight, catching up after downtime; `journalctl -u sunstone-update` shows what each run did, and `systemctl list-timers sunstone-update.timer` when the next is. Each run is `sunstone self-update --unattended`: the same update, without asking, with two rules of its own. It installs only a release newer than this one, no further than `hold_version`. And it leaves out a release whose install failed last time, until a newer one comes, so a broken release is not installed and rolled back every day; `sudo sunstone self-update --version X` tries it by hand. A run that fails and rolls back fails the unit, so `systemctl --failed` shows it. The timer ships disabled, as the service does.

**Holding a version.** `hold_version = "0.2.0"` under `[update]` keeps updates that pick the release themselves, the timer's among them, at or below 0.2.0; `--check` says what the hold keeps back. Naming a newer release with `--version` at the console still installs it.

**Behind a proxy.** `https_proxy = "http://proxy.example.com:3128"` under `[update]` sends self-update through a proxy that supports `CONNECT`; without it, `HTTPS_PROXY` from the environment, which the timer's service does not have. Credentials in the URL are refused, since settings end up in backups and support requests. Certificates are verified against the system's CA bundle and the CA certificates in `/etc/sunstone/ca.d/`, never the bundled interpreter's own paths. A proxy that inspects TLS presents certificates its own CA issued, which self-update refuses, naming `/etc/sunstone/ca.d/`: get the CA certificate from your security team, compare its fingerprint with theirs (`openssl x509 -noout -fingerprint -sha256 -in corp-ca.pem`), copy it there as a `.pem` or `.crt` file, and run `sudo sunstone self-update --check`. It changes trust for Sunstone only, not the rest of the host. A file there that is not a PEM certificate stops self-update, naming the file, rather than being skipped. Python checks certificates against OpenSSL's strict X.509 profile, which many inspection CAs issued before clients enforced it fail ("CA cert does not include key usage extension"): if yours does and cannot be reissued, `tls_strict_x509 = false` relaxes only that profile, still checking chains, validity, and host names. `api = "https://HOST/api/v3"` takes releases from a GitHub Enterprise server instead.

| Command | What happens |
|---|---|
| `sudo apt remove sunstone` | Stops the service and the update timer, and removes `/opt/sunstone` and the integration files. Keeps `/etc/sunstone` and `/var/lib/sunstone`. |
| `sudo apt purge sunstone` | Also removes `/etc/sunstone`, which holds the topology, on-call directory, and trusted CAs, self-update's directory, and the links that enabled the service and timer. Keeps saved state in `/var/lib/sunstone/state` and says so; remove it yourself to delete it. |

## Using it

- **Geographic:** sites and the links between them; line width is total capacity. Under each site's name, the transports it has circuits into ("INET · Mesa MPLS"). Click a site, or zoom in, to see its devices on rings around it (upper tiers inside), with a short stub for each circuit into a transport or link to an external node. The rings are a drawing aid: sources give coordinates per site, not per device.
- **Hierarchy:** sites with a core tier on top, other sites below by WAN hops. Transports are clouds on a level of their own between the sites whose circuits go into them, and external nodes go below the sites their links come from. Double-click a site, or use the details panel, to expand it into tier rows (WAN edge, core, distribution, access). Interface names label the selected device's links, and every link once zoomed in. Networks over 400 devices open with sites collapsed.
- **Topology:** automatic layouts, either of the whole network (collapsible sites, as in the hierarchy) or of a **neighborhood**: the devices within 1–4 hops of a device, site, or link. Choose a force-directed layout, optionally grouped into a frame per site, or a radial one with the center in the middle and a ring per hop. Open a neighborhood with **Show neighborhood** in the details panel or by double-clicking a device; double-click another device to walk on from there. Neighborhoods stop at 400 devices, adding whole hops only, and say what the next hop would have added. Nodes can be dragged, and finished layouts are kept while the page is open, so switching views and back shows the same picture. **Saved layouts** stores the current picture, settings included, under a name on the server, to open again later. Transports and external nodes are drawn too; a neighborhood stops at them.
- **Logical:** the named networks chosen in the header, or every one, without geography. Sites are boxes; double-click one to see its devices in those networks, and its frame to fold it again. A transport (a cloud), a fabric (a hexagon its members join, hubs marked), and an external node (dashed: outside the boundary) each have a place of their own, abstract rather than geographic. A network's links are drawn as they are, its tunnels dashed, in its color. What the networks shown ride is drawn faintly, only at their own sites, so choosing a tenant's network brings forward the places of the network it rides: red-alpha shows its five grey sites, with grey, blue, and the circuits under them. **Show what they ride** turns that off. With Live on, tunnels spokes have built to each other at the moment are drawn too, thinner and with shorter dashes, and the line above says how many ("corp · 20 sites · 4 spoke to spoke now"); they come and go without moving the view.
- **Networks** (header menu, search, or `?network=grey,blue` in a link): show one or more named networks in every view. Listed from the bottom of the stack up, each with what it rides; its color says how deep it sits: aqua over the circuits, violet over another network, orange three or more deep. The map draws their tunnels, and the tunnels their fabrics are made of, as dashed arcs between sites, bowed apart where networks share a pair of sites, and fades everything not in them; the graph views highlight them. While live state is shown, tunnels take the color of their health instead: up, down, partly down where an edge or arc stands for several, and gray where the source does not report them; spoke-to-spoke tunnels built on demand at the moment appear on the map too, thinner. Choosing a network in search shows it and selects it; its details say what it rides and what rides it, and list its tunnels, fabrics, sites, and what is beyond the boundary. A transport's details list its circuits and their state; an external node's, where it is connected and the tunnels to it; a tunnel's, its two ends and their sources; a fabric's, its members and how many tunnels it makes; a tenant's, its networks and nodes. Anything someone else runs says it is outside the boundary and known from our end only.
- **Network status** (with Live): the whole network (named in the topology: Enterprise in the samples) and each named network are **operational**, **degraded**, or **offline**, and so is each of their regions, sites, and locations. A device down degrades its own group; a link or tunnel down degrades the group it belongs to (the lowest holding both its ends; for a circuit into a transport, the whole) and every group below that holding one of its ends; a group no anchor reaches is offline, and every group above it degraded; a degraded group does not degrade the one above it by itself; and a group whose parts (the groups directly inside it, and the devices in it directly) reach each other less well inside it than when everything works is partitioned, which is degraded. A network is offline when no two of its sites reach each other. A cable's or circuit's priority limits how far its outage climbs: a low one degrades its location and site at most, and an ignored one nothing (see Data); in the layered sample, a tenant's encryptor's cable down degrades only its site. A network that works over one degraded at its sites reads **operational\*** with that caveat: blue working while one of four Internet circuits at Houston is down. **Problems** lists the networks not working as they should first; the **Networks** menu shows each one's state; a network's details say why, how many of its sites are reached, what is degraded beneath it, and which regions, sites, and locations are not operational; a tunnel's details say whether it is up, and a fabric's which of its tunnels are down and which spokes have built tunnels to each other now; a site's details list the networks there with the site's status in each, the whole network first ("grey · Degraded · GREY-ATL-DAL down"; "red-alpha · Operational\* · blue degraded at DAL"), and clicking one selects it. **Events** lists tunnels going down and coming back. The wall display names the networks degraded or offline, and the handover lists the networks not working at its end, in its message too.
- **Resources:** what the enterprise depends on beyond its own networks, each with a status of its own: in the layered sample, Global Access (the ways out at the TIC gateways), Research Peering, Nimbus Cloud access, Acme Logistics, and Branch VPN. On the map, each is a hexagon amid its members' sites, with dotted lines to them; in the logical view, a hexagon joined by dotted lines to its members (a circuit's device, a tunnel's ends, a fabric, another resource). With Live on, each is colored by its status: **operational** while every member is up and its device reached from the core, **degraded** when any is down or cut off, **offline** when none can be used; gray otherwise. Clicking one selects it, and its members in every view. Its details give its status and why ("DAL-INET-01 down"), each member and how it is now (clicking one selects it), and the resources it is part of; a circuit's, tunnel's, or fabric's details name the resources it is in. **Problems** lists the resources degraded or offline after the networks, and the wall display and the handover list them too; a "what if" lists each resource it changes ("Global Access · Operational → Degraded · DAL-INET-01 down").
- **Paths:** choose **Path from here** on a device, then click or search for the destination. Paths cross transports, as traffic does, and never go through an external node. Across an E-Tree, a leaf reaches only the roots, so a path between two leaves turns at a root's router ("via Harbor E-Tree › dal-wan-02 › Harbor E-Tree"). Every shortest path is found (by number of links; there are no routing costs in the data), drawn in all three views with everything else faded, and listed hop by hop with the interfaces at each end in the details panel. The topology view's **Path** scope draws only the devices on those paths, force-directed or layered by hop.
- **Live** (header toggle): device status and link load over every view, refreshed every 10 seconds. Devices are up (blue), dropping packets (amber, `!`), down (red, `×`, octagon in the graph views), without a recent reading (gray, `?`), or not monitored (hollow). Links are colored by their busier direction, in blue bands up to 80% of capacity, then amber, then red from 95%; down links are dashed and links with no data dotted. Sites take their worst device's color and say how many devices are down. The details panel adds round-trip time and loss from each monitoring position and load out and in on every link. A device or link the source does not watch reads "not monitored", and one without a fresh reading "no data": neither is ever shown as 0%.
- **Problems** (header button, in live mode): everything live state shows wrong, most urgent first. Problems with a high-priority cable, circuit, or device come before all the rest, in a group of their own, **High priority**, marked High with a stripe beside them. Then devices the core cannot reach, one entry per connected group, so a branch that loses both circuits is "HOU cut off", not one entry per device. Then links down between devices the core still reaches, congested links (95% or more), packet loss, busy links (80% or more), and devices without a recent reading. Each entry says what it does to the network, for example "16 devices left without redundancy", and on a link someone downstream answers for first, who ("Alpha answers first"). An ignored cable or circuit raises no problem. An outage or link down also names each named network it takes something from, and what ("corp: 2 of 63 tunnels · BNA cut off"): what fixing it would bring back, with everything else still down, so two circuits down at one branch each say they would bring the branch back. Its details list those networks as a "what if" does, each status read from now to fixed ("Degraded → Operational"). Clicking one selects it, brings it into view, and shows its impact in every view. The details panel then lets you **acknowledge** it with a note ("On it: Pat · carrier ticket 4411"), which lasts until the problem clears or you withdraw it. Problems someone is on, and problems that open maintenance accounts for ("Planned: Carrier cutover"), are dimmed and listed after the rest of their kind; the count in the header and tab is of the problems no one is on yet. **By region** lists them under the region of the site they are at instead, and `j` steps through them in the order shown. With networks chosen in the header, the list keeps to the problems that are theirs, says how many it leaves out ("2 not in corp"), and lists only those networks and what they ride among the networks not working; the counts in the header and tab stay those of every problem.
- **Maintenance** (header button, live or not): windows open now, coming up, and ended in the last day. **Plan maintenance…** on a device, site, or link opens a form for what the work is, when, what it works on (add more from the selection), a note, and your name, which the browser remembers. **Check impact**, on the form or on any window, shows what the work would take down, starting from what live state shows down when Live is on. While a window is open, the problems and events it accounts for are marked planned, and the details panel lists the windows that touch whatever is selected.
- **History** (in live mode): a time slider under the header covers the last 24 hours in 5-minute steps, with a bar at each step as tall as how much went down then, so branch outages stand out. Moving it back replays that moment in every view, problems and impact included; **Play** steps forward a step a second, and **Back to now** returns to the present. The **Events** tab beside **Problems** lists every change, newest first, with devices at one site that changed together as one row ("PVD: 18 devices down"); clicking a row replays its moment and selects what changed. With networks chosen in the header, it lists only what is theirs, and a menu beside the categories keeps it to one region. Ignored cables and circuits going down and coming back are left out of it, and of the slider's bars. With a monitored device selected, the details panel charts its round trip from each monitoring position over the day, with down, packet loss, and no-data stretches marked under the chart, and gives each of its links a small load chart; a selected link gets a chart of its load each way. Clicking a chart replays that moment.
- **What if:** **What if it fails?** on a device, site, or link shows what its failure would do: which devices it would cut off from the core, and which would be left depending on a single device (the panel names it). **Networks** under it follows the failure through every named network it reaches: each one's status before and after, the tunnels it would lose out of how many, the circuits it would lose at each site out of how many it has there, and the sites it would cut off; a network that stays up says so, and why it carries a caveat ("Stays up, over black degraded at HOU"). Failing hou-wsw-01 in the layered sample takes 2 of Houston's 4 circuits from black, and blue, grey, and red-alpha stay up over the other two; failing hou-blu-01 takes Houston off blue, grey, and red-alpha. **Show their tunnels** shows the networks that lose tunnels, so the map draws them. A circuit's details also offer **What if Mesa Carrier fails?**, which fails every circuit that carrier provides. Add more failures to see them together, and remove them one by one. In live mode it starts from what is already down. It is worked out only when asked: selecting something asks the server nothing.
- **Shared risk:** tunnels that look like separate paths in their own network but fail together. A network's details list what beneath it would take two or more of its tunnels down at once on its own: a device, a link, or every circuit of one provider, with the sites of it that would be cut off, worst first. Items with the same consequence are one line (in blue's: "atl-wan-01, atl-wan-01 – atl-blu-01, Circuit ATL-INET-01", then "2 of 9 tunnels · cuts off ATL"), and **What if** shows one failing. In the layered sample, Northwind Fiber takes 6 of grey's 15 tunnels and cuts off ATL, CLT, and RDU, though each of those sites has two grey tunnels; Mesa Carrier takes 32 of corp's 62 (its MPLS tunnels, and the MACsec over its E-LAN) and cuts off FTW, MEM, and BNA, and both of dci's MACsec connections over its E-Lines. A tunnel's details list the risks it shares, and with which tunnels. A tunnel's own ends are left out: that a router takes the tunnels it ends is plain to see. With Live on, the list is worked out on top of what is down at the moment shown: only what is still up counts, and a risk only because of what is down is marked **New** and comes first. With IAD's Northwind circuit down, the Bluebonnet one beside it is new: alone it would take 7 of grey's 15 tunnels, 5 of blue's 9, and 15 of corp's 62.
- **Impact** is drawn like a path, with everything unaffected faded: failed devices red with `×` (octagons in the graph views), cut-off devices as red outlines, devices left without redundancy amber with `!`, and lost links dashed red (amber where only some of a bundle are lost). The tunnels a "what if" takes down are drawn the same way, on the map for the networks shown and in the logical view.
- **Selection** is shared: whatever is selected stays selected when switching views. The details panel shows a device's neighbors interface by interface, a site's links to other sites, or a link's ends and circuit. Names in it are clickable.
- **Connections:** a link's details say what carries it and what it is for. **CID** is the enterprise's own ID for it (on our own cable, its cable ID), and **Carrier CID** the carrier's, each written once when both sides share it and side by side when they differ ("AUS-SAT-01 (A) · SAT-AUS-01 (Z)"); into a shared transport, only the A side has one. **Path** says whether it is our own cable, a provider's cross-connect (as between co-location cages), or a carrier's circuit, and from whom; **Service**, the layer-2 service it is part of ("E-Line · VPWS", "E-LAN · VPLS · over E-Access", "E-Tree · MPLS EVPN · leaf: reaches the roots only"); **Medium**, what carries the bits at our port; **Port channel**, the channel it is a member of, with the channel's own CID and how many members it has; **MACsec**, the MACsec connections on its ports, where each goes, and whether LLDP and CDP run inside it or alongside it in clear; **Neighbors**, what LLDP and CDP should show there, one thing or more ("The provider's equipment and the far end"; across a layer-2 service, our devices on it, and on an E-Tree leaf, the roots), MACsec or not. **Edge** gives its roles at the edge of the enterprise, as routing policy at its site sets them, each with what it does to the security boundary: **access** lets one endpoint in; **transit** carries our own traffic between our own sites and does not cross the boundary; **interconnect** exchanges traffic with one known network, as agreed; **ingress** lets outsiders in to the services we publish only; **egress** lets ours out, with inbound only as replies; **peering** exchanges routes with a known community; **open** exchanges them with the world. Where the far end leaves no doubt, a role is implied and says so: transit across a provider between two of our devices, access for a tenant's device, interconnect for a partner's, egress for an application's. A link between two of our own devices with no provider between them is internal, with no role. What a circuit into a transport is for only its routing policy can say, so until the topology says, it is **TBD**. **Priority** says how far its outage climbs, and where that comes from ("Low · access, by default · degrades its site at most", "High · set on the link"), and **Responsible** who answers for it first: the enterprise, or for access and interconnect alone, the party downstream ("Alpha (tenant)"); a port channel's members each give theirs, and a device that sets one gives it in its details. Tunnels and fabrics have the same section: their CIDs, the provider whose service they are, if any, and their roles (transit between our devices); a MACsec connection's also says what it is carried on (Circuit DAL-ELAN-01 and Circuit FTW-ELAN-01). Selecting a port channel's links together (clicking the bundle, or its CID in search) gives the channel's CID and each member's own IDs, its cable or circuit ID and the carrier's.
- **Search** (`/` or `Ctrl+K`) finds anything by what you have in hand: a device by name or management address, every device in an address range (`10.1.0.0/16`), a site by code, name, or region, a link by either CID (or any part of a carrier's: `KXFU/204411`), carrier, the device and interface at either end (`dal-core-01 Te1/0/3`, short or spelled out), its role at the edge ("egress", or "tbd" for those no one has given one), medium ("microwave"), or service ("e-line", "e-access", "802.1q-in-q"), a port channel by its CID (`DAL-IAD-PO01`) or channel interface, a transport by its service ("e-lan", "vpls"), MACsec ("macsec"), a named network, transport, external node, tunnel, fabric, or tenant by name, tag, or technology, and by the organization's word for what it is ("customer" finds tenants with `terms: {tenant: Customer}`), a resource by name, tag, or description, links and devices by priority ("high priority"; medium only where it is set), a problem by what it is about or the note on its acknowledgement ("ticket 4411"), a maintenance window by title or what it works on, and every command. Every word typed must match; exact names come first, then names they start, then words inside names, grouped by kind with the best group first. Choosing a result brings it into view in whichever view is open: expanding its site in the graph views, or moving the neighborhood. A problem shows its impact, a window opens the maintenance list on what it works on, and a command runs. Before anything is typed, search offers the last eight things looked at, remembered by the browser; with Live on, devices show their status.
- **Keys:** `1` `2` `3` switch views; `f` brings the selection into view and `0` shows the whole network; `n` opens the selection's neighborhood and `w` asks what if it fails; `l` turns Live on and off, `p`, `e`, `m`, `o`, and `d` show the problems, events, maintenance, on-call, and discovery lists, `h` opens the shift handover and `i` the incidents, `j` and `k` step through problems in the order the list has them, and `[` and `]` step back and forward 5 minutes; `c` copies the link. `Esc` cancels choosing a path's destination, then clears the selection. `?` (or the header's **?**) lists them all. Keys do nothing while typing in a box.
- **Back and Forward** (the browser's buttons, `Alt+←` and `Alt+→`, or a mouse's side buttons) go between places: going to another view, selection, neighborhood, path, problem, or "what if" adds a step, while moving the map, turning Live on, replaying, or clearing the selection changes the current step. Going back returns the map to where it was, or else brings the selection into view.
- **Links:** the address bar always holds a link to what is on screen: the view, the selection, Live and the replayed moment, a path, "what if" failures, the problem being shown, the topology view's settings, which sites are expanded, and where the map is. **Copy link** copies it. Opening it shows the same thing; anything in it that no longer matches the network (a renamed device, say) is skipped. Links stay readable, for example `?view=hierarchy&select=device:dal-core-01&live=1`.
- **On call** (header button, or `o`): who owns what and who to call. Each team owns part of the network (the samples have teams for WAN circuits, the data centers, each area, and the NOC for everything else), and the list shows, for each, what it owns, who is primary and secondary with their phone numbers, its manager, and until when, with who is on next. **Cover…** puts someone on call in place of a team's primary for a while ("Drew covers 14:00 – 18:00"), and the list shows covers until they end. The details panel says, for any device, site, or link, which team owns it and who is on call for it, and for a circuit, the carrier's NOC number and portal. Teams and people can be searched for. When replaying, the list shows who was on call then.
- **Paging:** a problem's details say which team owns it and whether it is urgent (outages, links down, and congestion are; packet loss, busy links, and missing readings wait for working hours), and whom a page would go to: the primary at once, then the secondary after 15 minutes, then the manager after 30, unless someone acknowledges it first. **Page** records the page; from then on the problem shows who has been told and who is next and when, the problems list marks it "Paged", and escalation stops when someone acknowledges the problem or it clears. **Nothing is sent**: a real paging service will do that once there is one. A problem cut off by circuits lists the carriers to call about them, with the carrier's CID to quote and ours beside it, and the wall display names the team and who is on call for each problem it shows.
- **Discovery** (`d`, or the **Discovery** tab beside the other lists): where the network and its documentation disagree, from the neighbor tables devices report over LLDP and CDP. It says how many documented links devices confirm, and how many tunnels, then lists, most misleading first: one of our own devices seen across a link for anything but transit (the boundary is not where it is documented: in the layered sample, our two data centers' routers see each other across the research network), two leaves of an E-Tree that see each other (Memphis and Oklahoma City, across Harbor E-Tree), a port with another device on it than documented, a cable on another port or a tunnel on another tunnel interface (BLUE-HOU-IAD's far end is really on iad-blu-01's Tunnel112), a documented link no one sees, a link no one documented, a circuit showing other than it says, a neighbor that is not in the topology, and a device that reports no neighbors at all (LLDP and CDP may be off on it). Circuits and links to someone else's device are checked by what each says LLDP and CDP show on our port: the far end, the provider's equipment (an NTU or PE), or nothing. A circuit showing something else, or a circuit into a transport that does not say, is a finding ("Circuit TPA-INET-01 shows the provider's equipment"); so is a carrier's circuit between two of our devices that is up yet shows nothing, since its provider passes nothing. A phone or a printer on a port no link documents is an endpoint on an access port: counted ("26 endpoints on access ports"), not a finding; a switch or a router there still is one. A device reports each neighbor over CDP, LLDP, or both, and describes it differently over each (a short name over one and the name with a domain over the other, or NX-OS's name with its chassis serial after it over CDP); rows on one port that name the same device, or give its management address, are one neighbor, and so is a row that names no one (an LLDP chassis ID alone) beside the one device seen over CDP, unless the port is documented to show two. A port can have several neighbors: across an E-LAN, each of our routers on it, and on an E-Tree, a leaf the roots. A port with MACsec is checked against what its link says it shows, as any other: CDP and LLDP may run inside the MACsec, reaching its far end whatever the provider passes, or alongside it in clear, beside the provider's NTU. Only where they run inside does seeing the far end vouch for the encryption too. Point-to-point tunnels are compared where CDP is seen over them, and a tunnel CDP does not run over is never a finding. Clicking a finding selects the link or device and brings it into view. The details panel says, for a device, whether it answered, how many of its links that should show something do (the far end, or the provider's equipment as documented), how many endpoints it has, and the findings that involve it; and for a link, its check: confirmed, the provider's equipment seen, nothing seen as documented, seen elsewhere, not as documented, not seen, down (so not seen), not said what it shows, or not checked; and for a tunnel, whether CDP over it confirms its far end, shows another, or does not run over it (for MACsec that LLDP and CDP run inside, whether its far end is seen inside it; for the rest, that discovery cannot vouch for it). Links that are down and devices that do not answer are not findings: discovery cannot see them, and Live already shows them. **Show on the map** (or clicking a finding, or `?discovery=1` in a link) draws it in every view, the way an impact is drawn, with everything that matches the documentation faded: cables seen but not documented as dashed violet lines, with a hollow mark for a neighbor not in the topology; documented links not seen as documented dotted; and the devices involved ringed. Clicking a seen cable selects the device it hangs off. Discovery follows the time slider: replaying a moment shows the run in effect then, list and map alike. Each finding says when it has been seen ("since 10:45", or "since before" the start of history when it goes back that far), and findings seen earlier in the day but not at the moment are listed after the rest with when they came and went, such as a lab switch that was plugged in for the afternoon. The simulated network is really cabled the way discovery sees it, so Live follows the real cables too: a link documented on one switch but plugged into the other reads as down, costs the redundancy the documentation counted on, and its problem says what discovery saw.
- **Fixing the documentation:** a finding the documentation can settle offers a fix under it: a link on another port or switch is moved to where its cable is seen, a cable no one documented is added (its speed from the port's type), a link no one sees is retired, and a circuit showing other than it says is documented as showing what is seen (the review gives what it said and what it would say). **Fix:** opens a review at the top of the Discovery list, with the finding on the map: the link as documented and as it would be, what Live reads now on the ports involved, and what the fix would do to redundancy and to the problems there are now ("dal-acc-05 would depend on dal-dist-02 alone", "Clears “dal-dist-01 – dal-acc-05 down”"). Live can argue against a fix: retiring a link that Live shows carrying traffic is warned against, since LLDP cannot see across a media converter. **Accept fix** takes a note and your name and changes the documentation for everyone: every view redraws with the fixed link selected, the finding goes, and live state, problems, impact, and discovery follow the fixed documentation, so a link now documented where its cable really is reads up. Fixes come from the latest run only, not while replaying. **Fixed here** at the foot of the list has every fix accepted, newest first, with who accepted it, when, and their note, and a fixed link's details say it was fixed here and is not yet in the source of truth; **Revert** takes a fix back out, unless a later one depends on it. A neighbor not in the topology and a device reporting no neighbors get no fix, and their details say why: the first needs the device documented, or unplugged; the second, LLDP or CDP turned on. Our own device across the boundary gets none either: someone has to find out whether the network or its documentation is wrong.
- **Expected findings:** what discovery cannot see, or what is not meant to be documented, can be marked expected instead of fixed: a link LLDP cannot see across a media converter, a lab switch on a lab port, a switch with LLDP off on purpose. **Mark expected…** under a link not seen, a neighbor not in the topology, or a device reporting no neighbors opens a review of what Live reads now on the ports involved (a link up and carrying traffic at both ends is likely there), and takes a note saying why, which it needs, and your name. The finding then leaves the list, the map, and the count on the tab, and is no longer offered for retiring; its link reads "Not seen, expected", with the note, in the details panel. A switch expected to report no neighbors covers its links too, while it does not answer discovery and each would otherwise be a finding of its own. **Expected**, near the foot of the Discovery list, has every expectation, with what discovery sees of it now, and **Withdraw** puts it back. A link on another port or device is not expected but fixed, and so is a cable no one documented.
- **Shift handover** (header button, `h`, or `?handover=12` in a link): what the incoming shift needs to know about the last 12 hours, or 8, over the whole window. **Open now** lists every problem there is, most urgent first, with the team that owns it and who is on it ("On it: Pat · carrier ticket 4411", "Paged, no one on it yet", "No one on it"), and says how many no one is on. **On call now** has each team's primary, with their phone, and secondary, until when. **Outages** are those that began or ended in the span, latest first, each with when and how long ("1 h 05 min", "25 min so far"): whole sites (devices at one site that went down together, with the links there that went down then, such as "HOU: 4 devices and 2 links down"), links on their own (mostly carrier circuits), and single devices, the first 10 of them until **Show all**. Then the pages and acknowledgements made, with the problems they were about even once cleared; maintenance open now, coming in as long again, and done; and the fixes and expectations recorded, and findings discovery first saw. Clicking something leaves the handover and shows it: a problem with its impact, an outage replayed at the moment it began, a team in the on-call list. **Print** puts it on paper, black on white in one column, and **Copy link** shares it. `Esc` or `h` closes it, leaving everything as it was.
- **Handover at shift change:** the NOC's shifts change at times the on-call directory sets (07:00 and 19:00 Dallas time in the samples). **Notes for the next shift**, at the top of the handover, are what the outgoing shift wants the next one to know: anyone writes one, with their name, and can withdraw it until the shift changes, when the header says it will be handed over. At each change, the handover of the shift ending then is saved as it stood, with the notes written during it. **Which handover** opens a saved one again (`?handover=20261028T0000Z`), with what was open and who was on call at the change; clicking a problem in it replays that moment while history still has it. **Message** shows the handover written to post in chat or send by email: a subject saying how much is open, the notes, the first 10 of each section, who is on call, and a link back. **Copy message** copies it; nothing is sent.
- **Signing for the handover:** someone from the incoming shift signs for the handover of their shift change once they have read it and taken over: under **Sign-off**, at the top of the saved handover, with their name and anything to say back to the outgoing shift. Until someone does, the header's button reads **Handover · to sign**, and the handover for now starts with **Not signed for**: how much was open at the change and the outgoing shift's notes, with **Read it and sign for it**. Then the saved handover says who took over and when ("Taken over by Sam at 07:12 · asked Pat about HOU"), and so do **Which handover** ("· Sam took over", or "· not signed for") and the message. Only the handover of the shift on now can be signed for, and only once.
- **Incidents** (`i`, or **Open incident** in a problem's details): a problem someone treats as an incident, named (the problem's title unless changed) and numbered. Other problems join it with **Add to incident 12** in theirs, and the problems list marks each one **Incident 12**. **Where it stands** says when it began, who opened it and how long after, who took it on and who was paged and how soon ("Pat · 06:22 · 7 min in"), and when it cleared or how long it has lasted. The **Timeline** is worked out from what Sunstone records about the devices and links its problems concern, from 15 minutes before it began: the changes the source saw, grouped by moment ("2 devices (hou-acc-01, hou-acc-02) down", "Circuit SAT-IAD-01 back up"); acknowledgements and pages, and each person a page reached as it escalated; maintenance beginning and ending; fixes to its links; the notes people add; and its own steps. Clicking a line replays that moment and selects what it is about. An incident clears when the last of its problems does, and follows a problem that comes back before it is closed. **Postmortem** closes it with a summary of what happened and what is to be done about it, which the handover asks for while it is missing ("cleared, postmortem to write"); after that nothing more is added. The **Postmortem** button shows the incident written to post in chat or send by email, with its timeline and a link back (`?incident=12`); nothing is sent. The shift handover lists the incidents open at its end or dealt with in it.
- **Wall display** (header button, or `?wall=1` in a link, with `&dwell=SECONDS` to change the default 20): for a NOC wall screen no one sits at. Live is always on; a bar across the top gives the time, how fresh the data is, and how many problems of each kind no one is on yet. The screen shows in turn the map and the hierarchy, each fitted to the whole network, then each of those problems close up with a large caption saying what and where. Moving the mouse shows controls (previous, pause, next, full screen, leave); `Space` pauses, the arrow keys step, `Esc` leaves.

## Data

The backend serves one topology file at `GET /api/topology`, with the fixes accepted into it applied (see below). The format is YAML with three lists, and more, all optional, for what is layered over them (below):

```yaml
sites:
- {code: DAL, name: Dallas DC, region: South, lat: 32.7767, lon: -96.797}
devices:
- {name: dal-core-01, site: DAL, role: core, platform: N9K-C9364C, mgmt_ip: 10.1.0.3}
links:
- a: {device: dal-core-01, interface: HundredGigE1/0/3, lag: Port-channel1}
  b: {device: dal-core-02, interface: HundredGigE1/0/3, lag: Port-channel1}
  speed_mbps: 100000
- a: {device: hou-wan-01, interface: TenGigabitEthernet1/0/3}
  b: {device: dal-wan-01, interface: TenGigabitEthernet1/0/1}
  speed_mbps: 10000
  kind: wan
  circuit: {provider: Mesa Carrier, circuit_id: ME-595185}
  enterprise_cid: HOU-DAL-01      # the enterprise's own; on a cable, its cable ID
```

Roles are `wan-edge`, `core`, `distribution`, and `access`. Each link end is a device name plus an interface name, which is the shape NetBox cables, LLDP/CDP neighbor tables, and NMS exports all reduce to. The loader rejects unknown keys, duplicate names, references to missing sites or devices, and an interface used by two links, and it reports every problem at once.

Groups, for status, also take NetBox's names:

```yaml
name: Enterprise                # or Global, Nationwide; without one, Network
regions:                        # regions inside regions; without them, a site's region stands alone
- {name: Central}
- {name: South, parent: Central}
locations:                      # parts of a site, inside each other: buildings, floors, halls
- {site: DAL, name: Hall A}
- {site: DAL, name: Cage 4, parent: Hall A}
devices:
- {name: dal-core-01, site: DAL, role: core, location: Hall A}
networks:
- name: grey
  anchors: [DAL, IAD]           # where it is reached from
  regions:                      # its own regions, when not the sites'
    grey-west: [DAL, HOU, OKC, TPA]
    grey-east: [IAD, ATL, CLT, MEM, BNA, RDU]
```

A site's `region` names one of `regions`, when there are any. A device's `location` is one at its own site. Without `anchors`, a network is reached from its sites with core devices, or else the largest group of its sites that reach each other; the whole network is reached from its core devices, as impact is.

A link's B end can be a transport or an external node instead of a device; its A end is always a device. For a circuit, `a` is its A side and `b` its Z side, as on the circuit order (for a circuit into a transport, the Z side is the transport), and Sunstone calls them that wherever it shows a circuit's ends and the load each way (A→Z, Z→A); a cable's ends are its A and B ends, as NetBox names them. A network is everything that carries it: the links that say so, with the VLAN, VXLAN VNI, MPLS label, or VRF each end knows it by (the same at both ends unless an end says otherwise), circuits into a transport whose network it is, and its own tunnels and fabrics. Each tunnel and fabric says which network it rides, so networks stack, and one network's tunnels can ride different networks: grey rides blue where there is blue, and black elsewhere. A tunnel's far end can be an external node known only by name and address (`b: {external: Acme Logistics, peer: 198.51.100.7}`). A fabric's tunnels are worked out from its members: each spoke to each hub, spokes to each other on demand for `hub-spoke-dynamic`, every pair for `full-mesh`, and none for `group` (GETVPN), whose members reach each other directly. `technology` is a label; `shape` is what Sunstone draws. `tags` on networks, transports, external nodes, tunnels, and fabrics are found by search. `terms` gives the organization's word for `network`, `transport`, `external`, `application`, `partner`, `tenant`, `tunnel`, or `fabric`, used everywhere Sunstone names them. The loader also rejects unknown networks, transports, external nodes, and tenants; a network that rides itself, through any number of others; a tunnel interface used twice, or one that is cabled; a tunnel leaving from a cabled interface that does not carry what it rides; a circuit into a transport that is not `kind: wan`, or that carries another network than the transport's; and fabric members that do not fit its shape.

Each connection also says what carries it and what it is for. `medium` is what carries the bits at our port. A link with a `circuit` crosses a provider's path: a carrier's service (`type: carrier`, the default), or the provider's cable (`type: cross-connect`, as between co-location cages); one without is our own cable, fiber, or radio. `circuit_id` is the carrier's CID, as the carrier writes it, so it can hold several (the local exchange carrier's beside the carrier's), and `enterprise_cid` the enterprise's own: on our own cable, its cable ID. Each is one value for both sides, or `{a: ..., z: ...}`: `z` left out is the same as `a`, and `z: ''` leaves the Z side blank; into a shared transport, a single value is the A side's only. Tunnels and fabrics take `enterprise_cid` too, and a `circuit` when they are a provider's service. `edges` lists a link's, tunnel's, or fabric's roles at the edge of the enterprise: `access`, `transit`, `interconnect`, `ingress`, `egress`, `peering`, and `open`. Without them, a role is implied where the far end leaves no doubt (transit across a provider's circuit or cross-connect between two of our devices, and for tunnels and fabrics between them; access for a tenant's node; interconnect for a partner's; egress for an application's), a link between two of our devices with nothing between them is internal, and a circuit into a transport is TBD. A transport joins only the circuits into it that are for transit, or TBD: reach, paths, the tunnels riding the transport's network, and status go across it by those alone. `neighbors` says what LLDP and CDP show on our port: `far-end`, `provider` (its NTU or PE), or `nothing`, or a list of the first two, as for a circuit whose NTU answers LLDP while CDP passes through to the far end; between two of our devices it is the far end unless it says otherwise, and into a transport or to an external node it is not said until it is.

A transport can be a layer-2 service, `service: e-lan` (many to many: VPLS, EVPN) or `e-tree` (one to many: EVPN with root and leaf policies), with a `technology` label; without one it is routed. Across a layer-2 service our own devices see each other, so a circuit into one can show the far end: the other devices on it, or for an E-Tree leaf, the roots. Each circuit into an E-Tree is a `role: root` on its transport end, or a leaf. A leaf reaches only the roots: reach, paths, status, and "what if" go from one leaf to another through a root's router, and a leaf no root reaches is cut off from the E-Tree. A circuit takes a `service` and `technology` of its own when it is point to point: `e-line` (VPWS, a pseudowire, 802.1Q-in-Q, a trunk carrying our VLANs across), or `e-access` (from a UNI to another operator's NNI, as a local exchange carrier's access to the carrier is). MACsec is a tunnel with `kind: macsec`: its ends are the physical ports of the link it rides, or of two circuits into one layer-2 service, it has no source, and it is up while those links are; its far end can be an external node its link goes to. Its `neighbors` says how LLDP and CDP relate to it: they run `inside` it, `alongside` it in clear, or `none`; what the port shows is still its link's to say. `lags` lists port channels between two of our devices, each by its two channel interfaces, with an `enterprise_cid` and a `circuit` of its own; its members, one or more, are the links whose ends name it with `lag`, each with its own IDs. The loader rejects a circuit into a routed transport that shows the far end, the provider's equipment on a link without a circuit, a role or a kind of neighbor named twice, `nothing` with anything else, a tunnel other than MACsec saying how LLDP and CDP relate to it, a root into anything but an E-Tree, an E-Tree with no root, an E-Line into a transport, MACsec on a port no link uses, with a source, between ports no one link or layer-2 service joins, between two leaves, or twice between the same ports, and a port channel listed twice, with no members, or with a member ending elsewhere than its far channel.


Every cable and circuit is part of the enterprise, and has a priority that says how far its outage climbs and how urgent its problems are; resources gather what the enterprise depends on beyond its own networks, each with a status of its own:

```yaml
priorities: {interconnect: medium}   # defaults by role, internal, or tbd, in place of the built-in ones
devices:
- {name: iad-wan-02, site: IAD, role: wan-edge, priority: high}   # its cables and circuits, and its own problems
links:
- a: {device: dal-wan-01, interface: GigabitEthernet0/0/0}
  b: {transport: INET}
  enterprise_cid: DAL-INET-01
  edges: [transit, egress, ingress]
  priority: high                # its own, before its devices' and its roles'
resources:
- name: Global Access
  description: Ways out to the world at the TIC gateways
  tags: [tic]
  circuits: [DAL-INET-01, DAL-INET-02, DAL-REN-01, IAD-INET-01, IAD-INET-02]   # by enterprise CID
- name: Nimbus Cloud access
  circuits: [IAD-NIMBUS-01]
  resources: [Global Access]    # resources inside resources
- {name: Acme Logistics, tunnels: [Acme VPN]}
- {name: Branch VPN, fabrics: [DMVPN-INET, DMVPN-MPLS]}
```

`priority` is `ignored`, `low`, `medium`, or `high` (written out: YAML reads a bare `off` as false). A cable or circuit down that is ignored counts toward no status and raises no problem, as an access port users come and go on; a low one degrades its location and site, never its region, the whole network, or a named network above the site; a medium one climbs as far as the status rules take it; and a high one climbs too, and its problems come first, marked High. A link's own `priority` comes first; then one its devices or its far end (an external node) give, the higher where both ends give one; then the default for its roles, the highest where it has several: low for access and interconnect, which the party downstream answers for first (the tenant, partner, or application at the far end, or the transport's provider), and medium for the rest, internal cables and TBD circuits included. `priorities` changes the defaults by role, `internal`, or `tbd`. Nothing is high unless the topology says so. A device's `high` also puts its own problems first. Priorities change only how far a link's own outage climbs: a site cut off is still offline, and raises every level, whatever its circuits' priorities, and a partition is still degraded.

`resources` lists what the enterprise depends on beyond its own networks: a way out to the world, a cloud, a partner. Its members are `circuits`, by the enterprise CID of either side (a cable's too), and `tunnels`, `fabrics`, and other `resources`, by name. A resource is operational while every member is: a circuit or a tunnel up with its device reached from the core, a fabric with all its tunnels up (a group, with all its members reached), and each resource inside it operational. It is offline when none of them can be used, and degraded otherwise. It counts its members whatever their priorities. The loader rejects an unknown priority or role in `priorities`, a resource named twice or with no members, a circuit no link has or that two links have, an unknown tunnel, fabric, or resource, a member listed twice, and a resource inside itself.

Live state comes from `GET /api/state`: one snapshot of everything a state source monitors, with two kinds of record, in the shapes monitoring tools such as vakr produce. Each **device** record says up or down and gives round-trip time and loss from each monitoring position; each **interface** record, keyed by device and interface name, gives operational status and percent load in and out. Sunstone works out each link from the interfaces at its two ends, so a link has data if either end is monitored; a circuit into a transport, or a link to an external node, has one end to read. Anything absent is not monitored; anything `stale` is monitored without a fresh reading. Sources keep a day of history: `GET /api/state?at=<time>` returns the state as of any moment in it, `GET /api/events` the changes seen (devices and links going down and coming back, readings stopping and resuming, packet loss, load crossing 80% and 95%), and `GET /api/history/{device}` one device's readings at each 5-minute step. A source is any object with `snapshot`, `events`, `history`, and a `retention` (`StateSource` in `backend/src/sunstone/live.py`); the only one so far is `SimulatedState` (`simulate.py`). It is deterministic for a given moment, so every viewer sees the same picture and any moment can be replayed: it monitors every WAN edge, core, and distribution device and about half the access switches; load follows each site's time of day with a few WAN circuits running hot; and at any time a few devices are down, a few have stopped reporting, a few drop packets, and a few carrier circuits are down, each for 15 minutes to an hour, starting and ending at different times. In about a third of half-hours a branch loses all of its circuits. A device the monitoring positions cannot reach looks down, as it would to a real poller; transports join the devices whose circuits go into them. Snapshots also say which tunnels are up (`tunnels`: each point-to-point tunnel by name, and each tunnel a fabric is made of as `FABRIC:a~b`, with those built spoke to spoke on demand listed while they are up); a source that does not report a tunnel leaves it taken to be up. The simulator works them out from the bottom up: a tunnel is up when its ends reach each other through what it rides, around what has failed, so a circuit down takes down the blue tunnels over it and the grey ones over those, unless they find another way; a few tunnels also fail on their own for 15 minutes to an hour; and in each hub-spoke-dynamic fabric, one pair of spokes in 20 builds a tunnel for 15 minutes at a time. Events include tunnels going down and coming back (`tunnel-down`, `tunnel-up`, with `tunnel`). Round-trip time grows with distance from the two monitoring positions at the hub sites.

Problems, impacts, and status are worked out on the server. `GET /api/status?at=<time>` returns the whole network's status and each named network's (`status`, `reasons`, `caveats`, how many `sites` and how many `reached`, `tunnels_down`, and the `groups` not operational, each with its `kind`, `id`, `status`, and `reasons`), and each resource's (`status`, `reasons`, and its `members`, each with its `kind`, `name`, `status`, `reason`, and for a circuit its `link`), for the same moment as the state shown. `GET /api/problems?at=<time>` returns the problems in the state as of a moment (pass the `generated_at` of the state shown, so the two match), each with what it does to the network, and for an outage or link down, `networks`: each named network fixing it would give something back to or change the status of, as `POST /api/impact` gives them, `before` with it fixed and `after` as things are; `POST /api/impact` answers a "what if": given devices, sites, links, and providers (`{kind: provider, id}`, every circuit it provides) to suppose failed, and optionally the moment whose live state to start from, it returns which devices they would cut off, which they would leave without redundancy, whether everything named was down or cut off already, and `networks`: the whole network and each named network they change, bottom up, each with its status `before`, its status `after` (as `GET /api/status` gives it), how many `tunnels` it has, and the `tunnels_lost`, `links_lost`, and `sites_lost`; and `resources`, each resource they change, with its status `before` and `after`. `GET /api/risks` returns each named network with two or more tunnels, bottom up, with its shared risks worst first: each a list of `items` (`kind` `device`, `link`, or `provider`, and `id`) that would each, failing alone on the network as documented, take down the same `tunnels` and cut off the same `sites`; at most 40 per network, with how many `more`. With `at=<time>`, they are worked out on top of what is down at that moment (`at` says which), and a risk only because of it is `new` and comes first.

Maintenance windows and acknowledgements go in another JSON file beside the topology (`small.operations.json`), or wherever `--operations` says, kept the same way and also ignored by git. Windows are listed, planned, changed, and deleted at `GET`/`POST /api/maintenance` and `PUT`/`DELETE /api/maintenance/{id}`; a window names devices, sites, and links that must exist in the topology, and lasts at most 7 days. `POST /api/acks` acknowledges a problem there is now, by its id, and `DELETE /api/acks?problem=<id>` withdraws it. Problems from `GET /api/problems` carry their `priority` (`high` ones come first), who answers for them first when it is not the enterprise (`responsible`), the windows that account for them (`planned`), their acknowledgement (`ack`), the team that owns them (`team`), whether they are urgent (`urgency`), and where their page stands (`paging`); events carry `planned`. `POST /api/pages` records a page to the team that owns a problem there is now, and `DELETE /api/pages?problem=<id>` withdraws it; `POST /api/covers` and `DELETE /api/covers/{id}` add and remove covers. Pages and covers go in the same file.

The on-call directory is a YAML file beside the topology (`small.oncall.yaml`), or wherever `--oncall` says; without one, everything else works and the on-call list says where to put it. `make data` writes one for each sample, with fictional people and phone numbers from the range set aside for fiction (555-0100 to 555-0199). An excerpt:

```yaml
people:
- {id: pat-rivera, name: Pat Rivera, phone: +1 214 555 0100}
teams:
- id: network-central
  name: Network Central
  rotation: {people: [pat-rivera, lee-chen], every_days: 7, handoff: '09:00', timezone: America/Chicago, starts: '2026-01-05'}
  manager: dana-novak
  escalation:                      # the default
  - {after_min: 0, to: primary}
  - {after_min: 15, to: secondary}
  - {after_min: 30, to: manager}
routes:                            # tried in order; the first that matches owns it
- {team: wan, match: {kinds: [wan]}}
- {team: datacenter, match: {sites: [DAL, IAD]}}
- {team: network-central, match: {regions: [South]}}
- {team: noc}                      # no conditions: everything else
carriers:
- {provider: Mesa Carrier, phone: +1 800 555 0102, portal: 'https://noc.mesa.example'}
urgency: {loss: low}               # kinds left out keep their defaults
handovers: {at: ['07:00', '19:00'], timezone: America/Chicago}   # when the NOC's shifts change
```

A route's conditions (`sites`, `regions`, `roles`, `kinds`, `providers`) must all hold, each for any of the values listed: a site matches on its code and region, a device also on its role, a link on its kind and carrier and on the sites, regions, and roles at either end. Turns start at `starts` with the first person and hand over every `every_days` at `handoff` local time (quote it: unquoted, YAML reads `10:00` as a number); the next person in turn is secondary. `handovers` lists the local times the NOC's shifts change each day, each a handover; without it, none is saved. The loader rejects unknown keys, references to people, teams, sites, regions, and carriers that do not exist, unknown time zones, and escalation out of order, and reports every problem at once. `GET /api/oncall?at=<time>` returns each team's shift then and the next, with the people, carriers, and covers; `GET /api/ownership` returns the team that owns each site, device, and link.

Discovery comes from `GET /api/discovery?at=<time>`: the run in effect at a moment of the last day, or now, every 15 minutes, each compared with the topology once for every viewer. Findings carry `first_seen` and `last_seen`, the ends of the unbroken stretch of runs around the moment that show them (null when it reaches back as far as history goes, or is still seen in the latest run); `gone` lists findings of earlier runs not in this one, and `history_from` is the earliest run history has. It returns the devices that answered, the check of each documented link not confirmed (`provider` and `nothing` as documented, `mismatch`, `differs` from what it says it shows, `not-seen`, `down`, `unstated` for a link that does not say what it shows, or `unchecked`; the rest are confirmed), the findings, each with the documented and seen ends and the devices involved, every cable seen other than as documented (`seen`), for drawing, and how many `endpoints` each device has on ports no link documents. Neighbor rows carry what the neighbor says it is (`capabilities`: router, switch, access point, phone, host), its `mgmt_address`, and over LLDP its `chassis_id`; one that says only phone or host is an endpoint. Rows on one port naming one device, over either protocol or both, are one neighbor (see Using it). `tunnels` gives each point-to-point tunnel's check by CDP over it, and each MACsec connection's inside it: `confirmed`, `mismatch`, `quiet` (CDP does not run over it; never a finding), `not-seen` (MACsec that LLDP and CDP run inside, up, its far end not seen), `not-inside` (MACsec they run alongside or not at all, which discovery cannot vouch for), `down`, or `unchecked`; a finding about a tunnel names it in `tunnel`. Neighbor tables are matched to the topology however devices spell things: names with a domain or in another case, and ports in full or short form (`TenGigabitEthernet1/0/1` or `Te1/0/1`). A source is any object with `discover(at)` and an `interval` (`DiscoverySource` in `backend/src/sunstone/discovery.py`); the only one so far is `SimulatedDiscovery`. Every device the live state source watches and finds up answers, reporting each real cable whose ports are up, and across circuits and on links to someone else's device what is really there (`Beyond` in `cabling.py`): what each says it shows, the provider's NTU on a circuit into a transport that does not say, and phones and printers, up to three on each watched access switch. The simulated network's real cabling (`cabling.py`) differs from its documentation by about one of each kind per thousand links: a link with a media converter that hides each end from the other's LLDP, uplinks on another port or on the other switch of the distribution pair, cables between access switches, ports leading to lab switches not in the topology, and a switch with LLDP and CDP off. Across circuits, there is one of each: a carrier's circuit between two of our devices that passes nothing, though it does not say so; a circuit into a transport said to show nothing that shows its NTU; and, where two circuits into one transport are for something other than transit, a layer-2 path across it on which each router sees the other (in the layered sample, the research network's). They stay the same for a topology, as documentation drift does, except the lab switches, each plugged in for about half of all three-hour blocks. The live state simulator follows the same cabling: a documented port with no cable is down, and the port a cable really reaches carries its traffic. Some devices report over CDP with their platform and full port names, others over LLDP with a domain and short port names, and NX-OS devices over both: over CDP with their chassis serial after their name, over LLDP with their name alone or, one in four, only their chassis ID and management address. A provider's NTU answers over LLDP, and takes LLDP's frames, so across a circuit that shows it, the far end is seen over CDP alone. Across a layer-2 service, each circuit that shows the far end sees the others on it that do (an E-Tree leaf, the roots), and a port with MACsec that LLDP and CDP run inside sees only its MACsec far ends, while one they run alongside sees and is seen as any other. CDP runs over about two in three GRE tunnels, both ways while the tunnel is up. Across layer 2 and tunnels there is one more of each kind of drift: two leaves of an E-Tree that see each other, and a tunnel whose far end is on another tunnel interface than documented.

Fixes accepted into the documentation go in a JSON file beside the topology (`small.changes.json`), or wherever `--changes` says, also ignored by git. The topology file is left as it is: `GET /api/topology` serves it with the changes applied in turn, and everything else follows that. Each finding that discovery can fix carries a `fix`: its `kind` (`move`, `add`, `retire`, or `document`, which sets what a link says it shows), a `summary`, and the link `before` and `after`. `GET /api/review?finding=<id>` works out what accepting the fix of a finding in the latest run would do now: the ports it takes out of the documentation and puts in, with what Live reads on each (`removes`, `adds`), or for documenting what a link shows, which changes no port, its ports (`involved`); the devices it would leave depending on a single device (`exposed`), give a second way to the core again (`restored`), or leave with no documented way to the core at all (`cut_off`); and the problems it would clear and raise, by title. `POST /api/changes` accepts it, with `by` and an optional `note`; `GET /api/changes` lists the change set, newest first; `DELETE /api/changes/{id}` reverts a change, or answers 409 if a later one depends on it. With `expect: true` and a `note`, `POST /api/changes` marks a finding expected instead (a link not seen, a neighbor not in the topology, or a device reporting no neighbors; others answer 409), kept in the change set as a change of kind `expect` and withdrawn the same way; `GET /api/review?finding=<id>&expect=true` returns what Live reads now on the ports it is about (`involved`). `GET /api/discovery` sets expected findings aside: they move from `findings` to `expected`, their cables are not in `seen`, and the links not seen that they explain are checked `expected`. A not-seen link of a switch expected to report no neighbors is set aside too, with the switch's finding as its `covered_by`. A change that no longer applies to the topology file, as when the file is replaced, stops the server starting, naming the change and the file.

`GET /api/version` says which release is serving; self-update waits for it after a restart.

`GET /api/handover?hours=<1–24>` (12 if left out) returns the shift handover for the span ending now: the problems now, routed as `GET /api/problems` routes them; the outages that began or ended in the span (`title`, `target`, `devices`, `links`, `start` and `end`, null for before history and still down, and `planned`); the pages and acknowledgements made in it, newest first; maintenance that ended in the span, is open, or opens within as long again; the changes recorded in it; the discovery findings first seen in it and still seen; and who is on call now. Acknowledgements and pages keep their problem's `title` from when they were made. It also carries the `notes` written since the last shift change, the shifts' `timezone`, and the `message` (`subject` and `text`). `GET /api/handovers` lists the handovers saved at shift changes, latest first, each in a line (`id`, `since`, `until`, how many `problems`, `unhandled`, `outages`, `still_down`, and `notes`, and `signed`), with the `next` shift change and `current`, the id of the handover the shift on now took over with; `GET /api/handovers/{id}` returns one as it was saved, with its `id`, the notes written during its shift, and `signed` (`by`, `note`, and `at`), null until someone signs for it. `POST /api/handovers/{id}/sign-off` (`by`, and an optional `note`) signs for the current one, and answers 409 if it is not the current one or has been signed for already. `POST /api/shift-notes` (`text`, `by`) writes a note for the next shift, and `DELETE /api/shift-notes/{id}` withdraws one, or answers 409 once it has been handed over. Notes go in the operations file. Saved handovers go in a JSON file beside the topology (`small.handovers.json`), or wherever `--handovers` says, also ignored by git; the latest 60 are kept, a month of 12-hour shifts, at about 80 KB each on the 3,000-device sample.

`GET /api/incidents` lists the incidents, newest first, each in a line (`number`, `title`, `status`: `open`, `cleared`, or `closed`; `began`, `opened_at`, `opened_by`, `cleared_at`, `closed_at`, and the ids of its `problems`). `POST /api/incidents` (`problem`, `title`, `by`, and an optional first `note`) opens one from a problem there is now, answering 404 if there is no such problem and 409 if it is in an incident not yet closed. `GET /api/incidents/{number}` returns one: its `problems` (each as it was when it joined: `title`, `kind`, `target`, the `devices` and `links` it concerns, how many devices it left unreachable (`lost`) or without redundancy (`exposed`), when it `began`, who added it, and `cleared_at`), `notes`, `closed` (`summary`, `by`, `at`), the `timeline` (each entry with `at`, `kind`, `text`, `by`, a `target` to select, and `planned`), the first acknowledgement and page, and the `message`. `POST /api/incidents/{number}/problems` (`problem`, `by`) adds a problem, `POST /api/incidents/{number}/notes` (`text`, `by`) writes a note, and `POST /api/incidents/{number}/close` (`summary`, `by`) closes it; each answers 409 once it is closed. `GET /api/problems` gives each problem's `incident`. Incidents go in a JSON file beside the topology (`small.incidents.json`), or wherever `--incidents` says, also ignored by git: the latest 500, each with the timeline entries kept from elsewhere, about 3 KB for one with a short timeline.

Saved layouts go in a JSON file beside the topology (`small.yaml` → `small.layouts.json`), or wherever `--layouts` says. They are listed, fetched, saved, and deleted at `GET /api/layouts` and `GET`/`PUT`/`DELETE /api/layouts/{name}`. The file is rewritten whole on each change, by writing a new file and moving it into place, and holds at most 200 layouts. Layout files are ignored by git, since they are each user's own arrangements.

With `--state-dir`, or `state_dir` in a settings file, saved files all go in that directory instead, one per kind: `layouts.json`, `operations.json`, `changes.json`, `handovers.json`, and `incidents.json`. The package puts them in `/var/lib/sunstone/state`.

## Decisions so far

- **Stack matches vakr's** (FastAPI, uv, ruff, ty; SvelteKit, Vite, Vitest, Playwright; TypeScript types generated from the backend's OpenAPI schema), so the two projects share tooling and patterns.
- **Data sources, eventually:** NetBox/Nautobot, LLDP/CDP discovery, existing NMS and NOC tools, and vakr for metrics. vakr covers only some devices, so its data will be an optional overlay; a device never needs vakr data to appear on the map.
- **Scale target:** 500–5,000 devices. Views start grouped (sites as points on the map, collapsed sites in the hierarchy) and open up on demand.
- **Hierarchy layout** is a small fixed-row layout rather than ELK.js. Layered-graph algorithms put every link between two different rows, which splits a redundant pair joined by a peer link onto two rows; fixed tier rows keep pairs side by side. The full 3,000-device layout takes about 40 ms.
- **Topology layouts** use fcose, whose cost climbs steeply with size. Measured on the 3,000-device sample: 0.4 s with sites collapsed, but 18 s or more for one pass over the fully expanded network (and its fast draft mode piles sites on top of each other). Above 800 nodes the layout therefore goes site by site, each site's devices alone and then the sites among each other, with a final pass that pushes overlapping sites apart. That takes about 5 s for the full sample. Expanding one site in a graph of up to 300 nodes refines the current picture instead of starting over. Layouts run in a Web Worker on plain graph data, so the page stays usable while they work; a newer layout stops one still running.
- **Site frames are backdrops, not compound nodes.** Cytoscape spends much of its drawing time on compound nodes in large graphs: walking parents and children for every style change and every edge. Frames are therefore ordinary nodes drawn behind their devices, sized by the hierarchy layout or fitted around their devices in the topology view, and following them when a device or the frame is dragged. That halved the time the page is blocked drawing the expanded sample. While panning and zooming, the graph views move a picture of the graph rather than redrawing thousands of elements each frame.
- **Live colors** were checked with a color-vision validator rather than by eye. Healthy is blue, not green: green and red are nearly indistinguishable with red-green color blindness (ΔE 4 deuteranopic), while blue, amber, and red stay apart (worst ΔE 24). Glyphs, line styles, and the legend carry the same information, so color is never the only cue.
- **Live updates** poll every 10 seconds. A full snapshot of the 3,000-device sample is 1.7 MB, under 100 KB compressed. Server-Sent Events (which vakr's API plans) would replace polling once there is a real source.
- **One copy of each moment for every viewer.** Building a snapshot of the large sample takes about 0.2 s, compressing it 0.1 s, and finding its problems 0.2 s; done per request, about 30 viewers polling every 10 seconds would fill a core. The server rounds the present down to the polling interval and builds, compresses, and analyzes each moment once, keeping the last 16. While anyone is watching it builds each new moment as it begins, and at startup it works out the day's events in the background, so viewers rarely wait for either.
- **Impact** is measured against the core: every device with the core role, where the data centers, monitoring, and the way to other sites are. A device is cut off when no path of working devices and links reaches any core device, and has no redundancy when every such path runs through one same device. Both come from one depth-first search (articulation points) from a virtual root joined to all core devices, about 5 ms on the 3,000-device sample; a "what if" runs two. Redundancy lost counts only devices that had it before, so devices that were always single-homed do not crowd the list.
- **Outages are grouped, not guessed at.** Monitoring cannot tell a dead router from a live one behind a dead circuit, so an outage names the devices and links where reach stops (both, in that case) and counts what is cut off behind them, instead of claiming a root cause.
- **History comes from the source.** The simulator can work out any moment, so Sunstone stores nothing. A real source would have to keep history itself (vakr keeps time series), or Sunstone would have to record what it sees. Events are the source's too, at 5-minute steps; the backend keeps each step's faults and loads once worked out, so the day's events take about 2 s the first time on the 3,000-device sample (about 3,900 events) and 20 ms after.
- **History charts** follow the dataviz rules used for the live colors: two lines at most per chart (round trip from each position, or load each way), in violet and aqua, validated against each other and against the status colors with color blindness, each named in the key with its latest value. Down, packet-loss, and no-data stretches sit in a strip under the plot rather than on the lines. Hovering, or the arrow keys, read out every line at one time on a line above the chart, so the readout never covers the data or runs off the panel.
- **Planned means accounted for.** A window accounts for a device when it names the device or its site, for a link when it names the link or a device at either end, and for an outage when it accounts for every link where reach stops. A problem only partly covered is not marked planned: something else may be wrong too.
- **Routes, as alerting tools have them.** Ownership is a list of rules tried in order, first match wins, with a catch-all last, the way Alertmanager routes and PagerDuty event rules work, so a NOC can read it and the order settles overlaps (a WAN circuit at a data center is the WAN team's because that route comes first). Who owns each site, device, and link is worked out at startup, and again when the documentation changes: about 40 ms for the 3,000-device sample.
- **Paging is on paper.** Sunstone records who paged which team when, and works out escalation from that, the team's policy, the rotation, covers, and the problem's acknowledgement each time it is asked, rather than storing who was told: so it is always consistent with the directory and shows correctly when replaying. Each step goes to whoever holds its role when it comes due, so a page that escalates after a handover goes to the new secondary. Connecting PagerDuty or Opsgenie would replace the record with a real page and the worked-out steps with theirs.
- **Rotations hand over at local time.** A team's turns change at the same wall-clock time in its own time zone, so the handover stays at 09:00 across the change to and from summer time, and that week's turn is an hour shorter or longer.
- **Discovery finds only what it can see.** A link that is down is not seen whatever the cabling, and a device that does not answer cannot vouch for its links, so neither is a finding: the first is down in Live, the second not checked. A device that answers but sees nothing at all is one finding, not one per link. Each documented link gets at most one finding, so a swapped pair of cables reads as two links on other ports, not four contradictions.
- **One network, two views of it.** The simulator's live state and its discovery are both made from one record of how the network is really cabled, so they agree the way a real network's would: the link Live shows down is the one discovery sees on another switch, and the redundancy the documentation counts on is not there.
- **Seen cables are drawn on top, not laid out.** Cables discovery sees but the documentation does not have are added to the graph after the layout is worked out (a neighbor not in the topology beside the device it hangs off), so turning discovery on and off never moves anything.
- **One comparison per run for every viewer, kept for a day.** The server keeps every run's comparison back a day (`discovery_log.py`), works each out once, fills in the day in the background at startup, newest first so recent moments are ready soonest, and compares each new run as it comes; replaying any moment is then answered from memory. Like live history, it comes from the source: the simulator can work out any run again, so nothing is stored; a real collector would keep its own history, or the log would go on disk. A run takes about 0.45 s on the 3,000-device sample, so a whole day about 45 s of background work at startup (0.2 s on the small one); it took 0.35 s before NX-OS devices reported each neighbor over both protocols, which doubled the rows their neighbors give. Getting there meant not building a full live snapshot per run: discovery asks the simulator only who is up and which ports are down, which it knows without working out any load. Caching link ids and the simulator's fixed per-link numbers also made every live snapshot about a quarter faster (275 to 200 ms on the 3,000-device sample).
- **The documentation changes; the cables do not.** The simulated network's real cabling is worked out once, from the topology file, and each version of the documentation is matched against it (`Cabling.documenting`): a cable carries the documented link at either of its ends. So a link fixed to where its cable is reads up, a retired one still carries traffic, undocumented now, and discovery stops reporting what a fix settled. A real network needs nothing like this.
- **Everything follows the documentation as it is now, history included.** Accepting or reverting a fix works everything built from the topology out again (the impact index, ownership, the simulator, the discovery log): about 0.4 s on the 3,000-device sample, then about 1 s for the present moment and 0.4 s for the discovery run when first asked for, and the day's history in the background. Replaying an earlier moment reads it against today's documentation, the way a real source's readings, kept by device and interface, would be read: a fixed link reads up all day, and its finding is gone from the day's runs too. Keeping every version of the documentation would show what Sunstone showed at the time, at the cost of a topology per change.
- **Accepted in one step, after a review against the network now.** Whoever reviews a fix accepts it, as with an acknowledgement, rather than one person proposing and another approving: with no sign-in there is no telling them apart. The review is worked out on the server by building the network as it would be documented and comparing its redundancy, and its problems now, with today's: about 1 s on the 3,000-device sample. Problems are compared by title, since a moved link gets a new id.
- **A fix only where the documentation can settle the finding.** A neighbor not in the topology needs a device documented (site, role, and all), or more likely unplugged, and a device that sees nothing needs LLDP or CDP turned on; neither is a change to a link. Two cables swapped get no fix either, since moving either link would put two links on one port. Ports are documented spelled out (`TenGigabitEthernet1/0/48`), as the device names its own port where it answers discovery.
- **Expected findings are set aside as they are served, not when runs are compared.** Each run is still compared once and kept as discovery saw it, and marking a finding expected, or withdrawing it, changes no link, so nothing is worked out again: the next request sees it. Replaying an earlier moment applies the expectations there are now, as it reads history against today's documentation. An expectation is kept by the finding's id, which stays the same while the finding lasts, so a lab switch expected on its port is expected each time it is plugged in again.
- **Expected only for what discovery cannot settle.** A link not seen may be hidden from LLDP, a neighbor not in the topology may be on a lab port, and a switch may have LLDP off on purpose: discovery cannot tell. A link on another port or device, or a cable no one documented, is the documentation being wrong, so it is fixed instead. A switch that does not answer reports no table at all, so its links each become a finding of their own; one expected to see nothing covers them, or they would come back, offering to be retired, whenever it stops answering.
- **The change set sits beside the topology file, not in it.** The file stands for the source of truth, which Sunstone reads but does not write; the change set is what would be sent to it, applied on top at every start.
- **Handover outages come from events, grouped as the events list groups them.** Each device and link is down from one event to the next; devices at one site that went down at the same step are one outage, with the links at that site that went down then, so a branch losing its circuits reads as one line. As with problems, nothing is said about why. A device or link that came back with no event saying it went down was down before history begins. On the 3,000-device sample a 12-hour handover has about 190 outages: about 13 at whole sites, 36 circuits, and 140 single devices, so single devices come last and are folded after the first 10.
- **The handover is worked out on the server, for everyone alike,** from what it already keeps: about 0.1 s on the 3,000-device sample once the day's events are worked out at startup (about 3 s before then). It applies the same rule as live state, that acknowledgements and pages end when their problem clears, so a handover never shows one standing for a problem that is gone.
- **Acknowledgements and pages keep their problem's title.** Once a problem clears, its id ("down:dal-acc-05:TenGigabitEthernet1/0/1--dal-dist-01:TenGigabitEthernet1/0/7") is all that is left to say what it was, and working the title out again from the moment fails when the documentation has changed since. So each keeps the title it had when it was made.
- **Packaged as vakr is.** One `.deb` for Ubuntu 26.04 on amd64, built with nfpm in a clean container from the lockfiles, with everything installed under `/opt/sunstone`: its own Python 3.15 from python-build-standalone, a locked virtual environment, and the built web UI. Settings live in `/etc/sunstone` and saved state in `/var/lib/sunstone/state`. `/var/lib/sunstone` itself is root's, so the service account, which writes `state/`, cannot plant a package or backup in `update/` for root to install or restore, nor replace that directory. The package is 28 MB and takes 85 MB installed; it builds in about 70 s, and two builds of one commit are byte-identical (checked; SvelteKit's build stamp is the commit time, as vakr's). Nothing in it needs glibc newer than 2.17, and the build fails if that changes without the package saying so.
- **Self-update is Sunstone's own, modelled on vakr's.** It keeps vakr's order (verify before changing anything, back up, install with `apt-get` so dpkg's records stay right, check, roll back) without its daily timer, proxy settings, or trusted-CA commands. A release counts as working when the new version passes `sunstone check` and, if the service was running, answers as the new version within 90 s. A broken release that fails to start uses up systemd's start limit (five starts in ten minutes), which would also refuse the rollback's restart, so the update clears it before restarting; the package tests found this.
- **The daily update is opt-in, and never retries a failed release by itself.** The timer ships disabled, as vakr's does, since updating a NOC tool unattended is the operator's call. Left on, a broken release would otherwise be installed, fail its check, and be rolled back every day, restarting the service each time; so the timer leaves out the release the last update failed to install, judging by the record of the last update alone, until a newer one comes. Unlike vakr, it has no marker for releases that need an operator: nothing in Sunstone's updates needs one yet.
- **An inspecting proxy's CA is trusted by Sunstone, not the whole host.** CA certificates in `/etc/sunstone/ca.d/` are added to the system's bundle for self-update alone, as vakr does with its own directory; changing what every program on the host trusts is left to the host's administrators. Trust there only lets self-update reach GitHub: what it installs must still carry a signature from a key in the installed package, so a CA trusted by mistake cannot slip in a release. The strict X.509 profile stays on unless relaxed, since relaxing it accepts certificates Python otherwise refuses.
- **Releases are signed with Sunstone's own key**, in its own namespace, `sunstone-release`, so a vakr release signature can never pass for a Sunstone one, and the release tool is vakr's, copied with its own configuration. It refuses to release until CI has passed for the commit, so Sunstone now has a CI workflow running `make test`.
- **One version, in `VERSION`.** The Python package reads it (hatchling, as vakr), and the package, tag, and `sunstone --version` follow; `0.2.0-rc.1` becomes `0.2.0~rc.1` in the package so that it sorts before `0.2.0`.
- **PyYAML is built from source in the package build.** It publishes no wheel for Python 3.15 yet, so the build compiles its hash-checked source with hash-pinned build tools and without its optional C extension: pure Python, as development already uses. Everything else is a hash-checked wheel.
- **The package depends on `tzdata`.** The bundled interpreter reads time zones from `/usr/share/zoneinfo`, which minimal Ubuntu systems lack; without it the on-call directory's rotations fail to load and the service does not start. The package tests found this.
- **Nothing starts on installation, and the sample shows until replaced.** The package puts the small sample in `/etc/sunstone` only when there is no topology there, and its on-call directory only with it, since it names the sample's sites. Files in `/etc/sunstone` are never dpkg conffiles, so upgrades never stop to ask about them.
- **The handover lies over everything, which stays as it is.** Closing it returns to the same view, selection, and map, and clicking an item in it steers the views underneath. Printing leaves out all but the handover.
- **Shifts are the NOC's own, not the rotations'.** Rotations say who is paged, and hand over daily or weekly; the room works in shifts, usually two of 12 hours or three of 8, so the directory says when they change. Like rotations they change at local time, so the 07:00 handover stays at 07:00 across summer time and that night's shift is an hour longer or shorter.
- **An incident is what someone says it is.** Nothing opens one by itself, and problems join only when someone adds them, since only the people on shift know that a circuit down and a site cut off are one thing. It is numbered, so it can be named on a call.
- **An incident keeps its own timeline.** The source keeps a day of history, and cleared acknowledgements and pages are kept a day more, but a postmortem may be written a week later. So the entries worked out from them are kept with the incident when it clears, and merged in whenever it is looked at; notes and its own steps are its own already. Worked out on the server for every viewer, an incident's report takes about 0.05 s on the 3,000-device sample.
- **Closing does not wait for the problems to clear.** Usually the postmortem comes after, and the report and the handover ask for it then; but a problem can last because it is understood and accepted, and its incident still needs closing. A closed incident stops following its problems, and one that comes back starts a new incident.
- **The incoming shift signs once, by name, for its own handover only.** There is no sign-in, so they give their name, as everywhere else. A signature cannot be withdrawn or changed, so the history says who took over; a handover from an earlier shift that no one signed for stays unsigned, rather than being signed late by someone who did not take over with it. The signature is kept with the saved handover, which otherwise stays as it was; signing rewrites the saved handovers file, about 0.17 s with 60 saved on the 3,000-device sample (4.4 MB).
- **A handover is saved at its shift change, worked out from history as of that moment.** A background thread saves each one as its shift changes. One missed while Sunstone was not running is saved when it starts again, or when someone next lists them, as long as history still covers that whole shift, and comes out the same: the problems, pages, acknowledgements, and who was on call as they stood at the change, so a page cleared since shows as open. Once saved it stays as it was, whatever the documentation or maintenance does later. On the 3,000-device sample saving one takes about 3.4 s before the day's events are worked out, and a saved one is served in about 0.01 s.
- **Notes are written during the shift, not at its end.** A note goes with the first shift change after it is written, so whoever notices something at 03:00 writes it down then; it can be withdrawn until it is handed over, and is kept as it was after.
- **The message is written on the server,** in the shifts' own time zone, so posting it at each shift change later needs only the sending. It lists the first 10 of each section, whole sites and links before single devices, and on the 3,000-device sample comes to about 2,200 characters over 37 lines. The page adds the link back, since only it knows the address people use.
- **Acknowledgements last until the problem clears**, as in most NOC tools, then are kept a day so replaying shows them. Problem ids stay the same while a problem lasts, which is what an acknowledgement attaches to.
- **The simulator acts out maintenance.** Devices and links in an open window are down for all of it, as the work would take them down, so planned work shows up in every view, problem, and event the way it would on a real network. A real source needs nothing like this.
- **Problems and impacts are worked out on the server** (`impact.py`, `problems.py`), once per moment for every viewer, and the analysis lives in one place. The web UI keeps its own copy of the device and link health rules (`live.ts`) to color the views; the backend's copy (`LiveView`) follows the same rules, and each side's tests pin them.
- **The link is the state.** Rather than a separate "share" feature, the page keeps its address in step with what is on screen, so the address bar, bookmarks, and Copy link all work the same way, and a wall display is just a link opened on a screen. Only what differs from how Sunstone opens goes in, so links stay short and readable. A shared link to a problem names the problem; if it has cleared by the time someone opens the link, they see the network without it.
- **Search runs in the browser.** The page already holds the whole topology, so search needs no server round trip: building its index for the 3,000-device sample (about 9,000 entries) takes about 80 ms in the Playwright container, done while the browser is idle after loading, and each keystroke 1–10 ms (a single letter, which matches nearly everything, about 40 ms). Words in descriptions and notes must start a word, so "hou" does not match "without"; names match anywhere, so "core" finds `dalcore01`.
- **Keys, search, and the help share one list of commands** (`commands.ts`), so a shortcut cannot exist without being listed, and every command can be found by typing what it does. Plain letter keys never fire with `Ctrl`, `Alt`, or `⌘` held, so the browser's own shortcuts keep working.
- **Back follows places, not every change.** Every selection, view, and problem shown is a step, as clicking through pages would be; moving the map, the time slider, and Live update the current step instead, or Back would take hundreds of presses to get anywhere. The wall display never adds steps.
- **The wall shows only what needs someone.** Problems acknowledged or accounted for by planned work are counted in the bar but not shown one by one, so the wall keeps cycling through what is still open. It shows at most 10 problems in turn, most urgent first.
- **Map tiles** come from OpenFreeMap's hosted dark style; viewers' browsers need internet access.
- **A link can end beyond the network.** A circuit into the Internet or a carrier's private WAN is the circuit a NOC watches most, so it is a link like any other: monitored, a problem when down, counted for impact and paths, planned for, owned by carrier. Its B end is a transport or an external node; its A end is always one of the network's own devices, which keeps every part of Sunstone that reads links to one end to handle. The simulated cabling takes only the links between two devices (`cabled()` in `model.py`); discovery compares every link, each by what it says it shows (below).
- **A transport joins, an external node does not.** Reach, paths, and the simulator's monitoring pass through a transport as through a device, so a branch on Internet circuits alone reaches the core; but a transport is never named as the one device something depends on, and an outage stops at a circuit into one. A partner's or tenant's node leads nowhere: nothing transits someone else's network. Working out reach with the transport costs nothing measurable: about 7 ms on the 3,000-device sample with its Internet circuits.
- **What a connection is for is documented, not discovered.** A neighbor row says who is across a port: a name, a port, a platform, what it says it is. It cannot say what the connection is for: an Internet circuit and an MPLS circuit both show the provider's equipment, or nothing, and the same router answers over a transit tunnel and over a backdoor cable. What a connection is for is what routing policy at its site lets across it, and with whom, so it is documented, per connection and per site, several roles at once where the policy gives them (one Internet circuit can be transit for the tunnels over it, egress for local breakout, and ingress for a DMZ): the same research network is peering at one site and open at another. The roles are the user's: access, transit, interconnect, ingress (where the enterprise publishes its services), egress (where it uses others', or breaks out to the Internet), peering (routes exchanged with a known community), and open (with the world). Sunstone implies one only where the far end leaves no doubt, and says so; a circuit into a transport reads TBD until documented, rather than a guess. Discovery checks what it can against them: one of our own devices across anything but transit.
- **A transport joins only circuits for transit.** A circuit for peering, open, ingress, or egress alone carries none of our traffic between our sites, by the policy that makes it so, so reach, paths, the tunnels riding a transport's network, and status go across a transport by its transit circuits only, and TBD ones, as before roles were documented. Without this, the research network read as a second way out of IAD for every tunnel there, through DAL. Shared risk on the layered sample is the same as before it had the research network. The whole network's status follows the rule too, as the named networks' always did.
- **Each link says what LLDP and CDP show across it.** Whether a circuit passes our devices' LLDP and CDP, shows the provider's NTU, or shows nothing depends on the provider and the service, not on what the circuit is for, so each says, as `neighbors`. Between two of our devices it is the far end unless said otherwise, as cables have always been compared, so a carrier's circuit up yet showing nothing is a finding that offers to document it. A circuit into a transport that does not say is not checked, but whatever is seen on its port is still a finding, offering to document what was seen: a real collector's report of a provider's NTU is never left unmentioned, and documenting it takes one fix. A neighbor not in the topology on a circuit's port is the provider's equipment, and on a link to someone else's device, theirs.
- **An E-Tree's leaves reach the roots, and each other only through one** (the user's rule: leaves depend on the root, and with no root reached a leaf is cut off). Each leaf's circuit leads to a corner of the transport of its own, which every root's circuit reaches too, so reach, impact, status, the simulator, "what if", and paths all follow the rule without one of their own (`transport_hops`, mirrored in the browser's paths): a path between two leaves passes the root's router, and a root router alone is named as the one device the leaves depend on. A single node for the transport, as a routed transport has, would join leaves directly, which the service forbids, and would make a leaf with an Internet circuit a way out for the others.
- **MACsec is a connection of its own, written as a tunnel** (the user's choice over a list of its own or a property of the link). It is configured on the physical port, so its ends are ports a link uses and it has no source; it carries a network inside the boundary across the provider, as a tunnel's traffic is, and shares tunnels' status, events, drawing, details, and shared risk. Unlike a tunnel, it is not routed around a failure: it rides the link at its ports, or two circuits into one layer-2 service, and is down when any of them is, so a carrier failing takes it as it takes the circuits (Mesa takes both of dci's MACsec connections, on its two E-Lines). One MACsec connection is one far end; a port on an E-LAN has one to each device it talks to. LLDP and CDP may run inside a MACsec connection, alongside it in clear, or not reach its far end at all (the user's point), and a neighbor table cannot tell which: so what the port shows stays its link's to say, and the MACsec connection says only how LLDP and CDP relate to it. Where they run inside, its far end seen proves the encryption works; alongside, only the circuit, so discovery does not vouch for it.
- **One device, however the protocols describe it** (the user's rule). CDP and LLDP describe a neighbor differently: a short name and one with a domain, NX-OS's name with its chassis serial over CDP, an LLDP chassis ID with no system name. Rows on one port that name one device, or give its management address, are one neighbor; a row that names no one beside the one device seen over the other protocol is that device too. The exception is a port documented to show two kinds of neighbor, such as an NTU answering LLDP while CDP passes through to the far end: there a row that names no one is not taken for the far end. Without this, every NX-OS neighbor would be a second, unknown neighbor on its port.
- **What a port shows can be more than one thing** (the user's choice). A carrier's NTU often answers LLDP itself while CDP passes through the service to our far end, so `neighbors` takes a list, and a port is confirmed when it shows each thing it says and nothing else; one showing only some of them offers to document what it shows.
- **The service type is the carrier's, on transports and circuits** (the user's choice). E-LAN and E-Tree are multipoint, so they are transports, drawn as clouds; E-Line and E-Access are point to point, so they are a circuit's. Only E-LAN and E-Tree change reach and discovery; the rest, and `technology` (VPLS, MPLS EVPN, VXLAN EVPN, VPWS, 802.1Q-in-Q), are said and searched. An 802.1Q-in-Q trunk is a circuit that `carries` several networks, as any trunk does.
- **A port channel has a CID of its own, and its members name it** (the user's choice). Members already said which channel they are in (`lag`), as NetBox's interfaces do, so `lags` adds only what the channel itself goes by, the way a tunnel has a CID and rides links that have theirs; a channel of one member is still a channel. A fix that retires a channel's last member, or moves it off, retires the channel with it, rather than leaving documentation the loader would refuse.
- **CDP over a tunnel is compared where it is seen, and never missed** (agreed in milestone 23). CDP runs over some point-to-point GRE tunnels and not others, and over multipoint ones not at all, so a tunnel with no CDP neighbor is checked "without CDP", never a finding; one whose far end is another device, or another tunnel interface, is a finding with no fix (the user's choice), since fixes change links only. MACsec is checked on its port where LLDP and CDP run inside it: not seeing its far end there while up is its circuit's finding.
- **Endpoints are access, not findings.** A real collector sees every phone and printer on every access port, none of them documented, and would otherwise bury everything else. A neighbor that says it is only a phone or a host, on a port no link documents, is an endpoint, counted for its switch; one that says it is a switch, a router, or an access point stays a neighbor not in the topology, as the lab switches are.
- **One CID field, and the Z side as the A side unless said.** The enterprise's ID for a connection is a circuit ID on a circuit and a cable ID on a cable, in the same field (`enterprise_cid`), since staff quote whichever the connection has. Both it and the carrier's ID (`circuit_id`, free-form, since the local exchange carrier's ID often travels with the carrier's) are the same at both sides unless the Z side has its own or none, and a circuit into a shared transport has only an A side. A circuit is named by the enterprise's CID wherever Sunstone names it; the carrier's is given where staff call the carrier.
- **Networks are slices, not kinds of link.** A link says which networks it carries, with the numbers each end knows them by, since VLAN 30 at one end can be VLAN 400 at the other, and Tunnel12 can meet Tunnel36. Tunnels and fabrics are lists of their own, not links: impact and problems stay physical, since a tunnel counted as a link would be a second path beside the very circuit it rides, overstating redundancy. A "what if" follows failures through the layers separately (below).
- **NetBox's and Nautobot's names where they have the object**: tenants, provider networks (transports here), and tunnels with hub, spoke, and peer terminations, so importing from them later is a mapping, not a translation. An organization's own words for these (`terms`) go in the topology file and change only what is shown and what search finds; the file itself keeps Sunstone's keys, so there is one format.
- **A transport has no place on a map.** The map keeps to geography: sites name the transports they have circuits into, and tunnels are arcs between sites. The logical view gives transports and fabrics places of their own, abstract rather than geographic, with what the networks shown ride drawn faintly only at their own sites: the whole of the circuits under grey is every circuit there is. A layout puts a transport in the middle of the sites whose circuits go into it, often on the hubs or on a fabric over it, so afterwards transports, fabrics, and external nodes are moved off anything they landed on.
- **Colors say how deep a network sits, not its name.** Networks named red or blue are names; drawing them in those colors would make the red network read as down. Color shows depth instead: aqua over the circuits, violet over another, orange three or more deep, the reference palette's three hues that pass every color-vision check on this background with all pairs shown at once, run through the data-visualization validator. Violet is close to the live blue and orange to the live red, so tunnels are always dashed and named, and turn gray while live state is shown. The logical view of the 3,000-device sample (63 sites, the Internet, and a DMVPN fabric) lays out in 0.4–0.9 s in the worker and draws in about 12 ms.
- **Status by the rules agreed for it, worked out on the server.** Every group's state comes from what is down in the snapshot, as problems do, once per moment for every viewer: about 0.09 s on the 3,000-device sample (0.15 s before 0.6.0), in a moment that takes 0.58 s to build. Whether a group is partitioned is counted with each link once, at the group that owns it: only those can join its parts, since a link further down lies inside one of them. Counting every group's devices with every link inside it, as before, gave the same counts (checked on 4,200 random sets of failures in the three samples) and took most of the time. How deeply groups are defined decides what climbs: a site without locations keeps a floor cut off to itself, but a location cut off raises every level, as a site does. Links into a transport belong to the whole, so one of a site's four Internet circuits down degrades the site, its region, and the whole; that is why a large network's circuits read degraded nearly always, and why its regions and sites carry the useful part.
- **Every cable and circuit is the enterprise's; its priority says how far its outage climbs** (the user's model, over leaving connections that are not for transit out of the enterprise's status). The ratings are ignored, low, medium, and high: low stops at the site, ignored counts nowhere, medium climbs as every link did before, and high climbs too and comes first in Problems. The defaults follow who answers for a connection first: access and interconnect are the party downstream's (the tenant, partner, or application at the far end), so low; transit, ingress, egress, peering, and open are the enterprise's, so medium. Internal cables and TBD circuits are the enterprise's too, so medium (Sunstone's choice). Nothing starts high: the admins say what supports mission essential functions. In the layered sample, Alpha's encryptor's cable at DAL (DAL-C0022) down used to degrade the whole network, Central, South, grey, grey-west, and red-alpha; now it degrades DAL and Hall B in each, and red-alpha says that grey is degraded beneath it at DAL. The research network's open circuit at DAL is the enterprise's to answer for, so it still degrades the whole network and black, and Global Access with them. Status takes no longer for it: 50 ms on the 3,000-device sample with ten random links down, against 58 ms before (within run-to-run noise).
- **A priority limits only how far a link's own outage climbs.** Reach, offline, and partitions ignore it, so a site whose only way in is an ignored cable is still offline when the cable is down; and a resource counts its members whatever their priorities, so an ignored circuit in one still degrades it. An ignored cable or circuit raises no problem of its own, though an outage it causes is still one. Its outage is not hidden from the views: Live still draws it down.
- **Priorities are worked out in the browser too,** by the same rules as the server's (`priorities.ts` mirrors `ratings` in `model.py`, as `connections.ts` mirrors the roles), so link details can say where each comes from ("Low · access, by default", "High · set on the link"); problems carry theirs from the server.
- **A resource is judged by whether the enterprise can use its members** (the user's rule: operational when all are up and reached, degraded when any is down or cut off, offline when none can be used). Reached is from the core, as impact measures it, so a circuit up at a site cut off from the core is cut off. A fabric counts by the tunnels it always has, not those built spoke to spoke on demand, and a group fabric (GETVPN) by its members; a resource inside another is one member with its own status. Resources are worked out with the networks' status, once per moment for every viewer: 0.7 ms for the layered sample's five.
- **Offline is about the network, not where it is watched from.** A group no anchor reaches is offline, but the whole network is offline only when no two of its sites reach each other: sites cut off from the hubs still work together. Partitioned compares how a group's parts reach each other inside it with how they do when everything works, so sites joined only across the Internet are not partitioned for being built that way.
- **A tenant's network reaches across what it rides.** It has no tunnels of its own, so its handoffs reach each other when the network it rides joins them now: red-bravo loses Memphis when grey does.
- **Tunnels are worked out from the circuits up,** each riding a network whose own tunnels are already settled, so blue's state decides grey's. A tunnel to an external node is up while its device reaches a transport through what it rides. The physical status and impact still count only cables and circuits.
- **"What if" follows failures through the layers on the server.** The tunnels riding what fails are worked out again from the circuits up, as the simulator works them out: a tunnel live state shows down stays down, and spoke-to-spoke tunnels built now stay up while their ends reach each other. Every network's status is then worked out by the rules live status follows, both with and without the failures, so the two are compared alike. A network is listed when it loses a tunnel, a link, or a site, or its status, reasons, or caveats change; that is how "blue stays up" comes to be said, from the caveat black's lost circuits give it. What the failures are compared with, every status without them, is the same for every failure asked about at one moment, so it is worked out once for the healthy network and once for each live moment asked about, and kept for the last 16 moments. Through the API on the 3,000-device sample, a "what if" takes 90 ms on the healthy network and 106 ms at a live moment (0.34 s and 0.38 s before 0.6.0); eight people asking at once wait 0.9 s and 1.4 s at the median (2.1 s and 3.0 s before), since one server process works them out in turn. It is worked out only when someone asks: selecting something asks nothing.
- **Shared risk is what takes two or more tunnels down at once, on its own.** Every device and link in the networks beneath a network, other than its tunnels' own ends, and every provider of the circuits among them, is failed alone on the network as documented with everything up; those that take two or more of its tunnels are its shared risks, ranked by the sites they cut off, then the tunnels they take, so what a network cannot ride out comes first. A branch's one Internet circuit taking both its tunnels to the hubs is a risk, but its MPLS tunnels keep the branch in corp. A provider counts because its circuits fail together when it does, at different sites and into different transports; a transport does not, since the Internet as a whole does not fail. Worked out once per version of the documentation, in the background at startup: about 0.07 s on the layered sample (62 risks over 5 networks) and 0.1 s on the 3,000-device one (68 over corp). With Live on, they are worked out again on top of what is down, once for each set of things down and kept for the last 16 (0.08 s on the layered sample, 0.12 s on the 3,000-device one): only what is still up is failed, only tunnels still up count, and an item is new when it was no risk of that network on the network as documented. New items are a risk of their own, apart from old ones with the same consequence, so the one circuit left at a site does not hide among the provider and switches that were risks already.
- **A problem says what fixing it would bring back** (the user's choice over saying what it does on its own). Everything down now is compared with everything down but it, so when two circuits down at a branch only together take it off blue, each says fixing it brings the branch back, which is true of each and says what to fix; on its own, each would say that blue stays up, exactly when it does not. Fixing an outage brings back its devices down and every link down at it or inside it; a tunnel down while everything it rides works is down of its own accord and stays down. Only named networks are answered: the whole network's part is the problem's physical impact, and its status is most of the work (74 ms on the 3,000-device sample, against about 1 ms for each named network). Answers are worked out while each moment is built and kept for as long as the same things are down, since problems last minutes and moments come every 10 seconds: on the 3,000-device sample, about 55 ms for its 10 or so outages and links down when what is down changes, and 3 ms otherwise.
- **A partition is counted between a group's own parts:** the groups directly inside it, each taken as one, and the devices in it directly. Counting every device as a part made a site split inside itself read as its region and the whole network partitioned too, which rule 1 already keeps at the site; a "what if" of hou-blu-01 had the whole network "partitioned into 20 parts". The Internet joins the circuits into it, which belong to the whole, so sites joined only across it are not partitioned at the top.
- **Problems and events follow the networks chosen, by the logical view's rule.** Something is theirs if it is part of one of them, or of a network beneath one at that network's sites: with grey chosen, a circuit down at a grey site is grey's, though only black carries it, and one at a site grey does not reach is not. A problem is also theirs when it takes something from one of them, or when what it fails or cuts off is theirs. The header and tab keep counting every problem, so choosing a network never hides that something is wrong elsewhere, and the list says how many it leaves out.
- **Regions are the chosen network's own, else the topology's.** With one network chosen that names regions (grey-west, grey-east), problems and events go by those; otherwise by the region each site is in, and sites in none are in "No region". A problem goes under the region of its one site (its device's, its site, or its first link's A end); an event row is kept for a region when anything it is of is there, so a circuit between two regions shows under both. Events stay in time order, with the region a filter rather than a grouping, since what happened when is the point of them (the user's choice).
- **Spoke-to-spoke tunnels are drawn as live state reports them,** not listed in the topology: DMVPN-INET's 15 spokes in the layered sample could build 105, and only those up now are drawn (2 to 5 at a time over a simulated day, measured every 30 minutes). The logical graph is built again only when that set changes, and with the same layout the view keeps its zoom.
- **One page, prerendered with relative paths,** so the same build works at a site's root and under any path a reverse proxy gives it. SvelteKit writes a fallback page with paths from the root, so the single page is prerendered as an empty shell instead; it finds its files and the API (`api/...`) relative to itself, and SvelteKit works out the base from where the browser loaded it. A Playwright test plays a proxy at `/sunstone/` and fails if the page asks for anything outside it.

## Testing

`make test` runs backend tests (pytest), ruff, ty, svelte-check, prettier, frontend unit tests (Vitest), and the release tool's tests. CI runs it for every push to `main`. `make e2e` builds the UI and runs Playwright tests against the real backend. `make package-test` builds three test releases signed with a throwaway key, one that fails to start, and two that must be refused, then installs, runs, updates, rolls back, and removes them in a container booted with systemd; and runs the daily timer's update against a stand-in for GitHub whose certificate only a test CA in `/etc/sunstone/ca.d` vouches for, as behind an inspecting proxy: the broken release rolls back and is not tried again, the hold keeps the next back, and lifting it installs it.

Where Chromium's system libraries are missing, run the browser in the Playwright container and point the tests at it:

```console
$ docker run --rm --network host --init mcr.microsoft.com/playwright:v1.64.1-noble \
    /bin/sh -c "cd /tmp && npx -y playwright@1.64.1 run-server --port 3124 --host 127.0.0.1" &
$ PW_WS_ENDPOINT=ws://127.0.0.1:3124/ make e2e
```

## Releasing

A release is a GitHub release holding the `.deb`, `SHA256SUMS`, and `SHA256SUMS.sig`, cut with `tools/release` on the development host. The signing key is Sunstone's own, `~/.config/sunstone-release/release_ed25519` beside vakr's: passphrase-protected, never copied to GitHub or CI. `packaging/release-signers` lists its public half, which every package ships for self-update to check against; its fingerprint is `SHA256:8WUCE9gHrarTMP6hv8LpAeTHv04rWlzWYLNuxC3Q1Lk`.

1. Set `VERSION` (`MAJOR.MINOR.PATCH`, or `-rc.N` for a release candidate) and add its section to `CHANGELOG.md`.
2. Merge to `main` and push. CI must pass for that commit.
3. `make release-dry-run` runs every step except tag, push, and publish: the checks, `make deb`, `SHA256SUMS`, and the signature, verified against `packaging/release-signers`. It writes the notes to `dist/release/v<version>/release-notes.txt` and says which versions they cover, so they can be read before tagging.
4. `uv run tools/release/release.py`, run from the repository root, does it for real, asking for the key's passphrase: it tags `v<version>`, pushes the tag, and creates the release with the changelog's notes, marked as a normal release, release candidates included, so anyone can download and test it. It needs an authenticated `gh`.

**Notes that catch up.** The notes are the version's own changelog section. When versions between the last release tagged on GitHub and this one were never released, their sections come along, newest first, each under its own heading, after a line naming them: 0.6.0's notes carry 0.5.0, 0.4.0, and 0.3.0, since the last release was 0.2.0. Operators so read everything that changed since the release they have. With nothing skipped, the notes are the one section, as before. Sunstone's copy of the release tool differs from vakr's here; vakr's takes the one section only.

`make deb` builds a package from the work tree in a clean `ubuntu:26.04` container. Test builds, with `VERSION_OVERRIDE` (and `RELEASE_SIGNERS` to trust a test key), are for `make package-test` only; the release tool refuses them. To rotate the key, add the new one to `packaging/release-signers`, release that signed with the old key, and remove the old key in a later release.

## Measuring speed

Open the app with `?perf` (for example http://127.0.0.1:8000/?perf) to show, in a corner: frames per second, the worst frame in the last second, the longest stretch the page was blocked, and timings of the heavy work (layouts, drawing, live updates, map updates). `make bench` runs the same measurements over scripted scenarios on the large sample (zooming the map, live updates, expanding every site in the hierarchy and topology views) and prints a table. It takes `PW_WS_ENDPOINT` like `make e2e`, and `BENCH_HEADED=1` to watch it in a browser window.

The Playwright container draws without a GPU, so its frame rates say little about real screens: run `make bench`, or open `?perf`, on the machines people will use. Measured in the container on the large sample, before and after this round of work:

| | Before | After |
|---|---|---|
| Page blocked laying out the topology view, every site expanded | 5.1 s | 1.5 s (layout runs in a worker) |
| Page blocked expanding every site in the hierarchy | 1.8 s | 0.9 s |
| Live update, fetch to screen | 0.8–1.5 s | 30–50 ms |
| Problems for each update | 40–190 ms in every browser | 20–50 ms to fetch, worked out once on the server |
| First load of the day's events | 5.8 s | 0.2 s |
| Server time per viewer per update | about 0.35 s | none beyond sending a cached copy |

## Next

- Overrides: a local layer kept apart from fixes that survives re-import, each with a target, a kind (rename or alias, tags and labels, one device on this port, ignore a neighbor, hide from the map or status, lock a field against a source), a value, a note, who, when, and an optional expiry.
- Priorities in paging: a high-priority problem paging with high urgency, and one the party downstream answers for first going to them; urgency is by problem kind today.
- Resources chosen like a network, filtering the views to their members, and shared risk for each: what one device, link, or provider would take a resource down with.
- Port channels into a transport or to someone else's device, such as two circuits bundled to a provider's PE: channels are between two of our devices so far.
- MACsec with one connectivity association for several far ends on an E-LAN port, and to someone else's device in the samples (a cloud's direct circuit).
- Fixes for tunnels: moving a tunnel's documented end to the tunnel interface CDP shows.
- Roles checked against routing: once there is a source for BGP sessions and the prefixes exchanged, whether a circuit for peering exchanges routes only with its community, and one for egress takes none in.
- Sources: NetBox/Nautobot import, then NMS import and LLDP/CDP discovery.
- Paging for real: PagerDuty or Opsgenie for pages and schedules, so the directory and the paging service cannot disagree.
- The handover posted to chat or email at each shift change: the message is written, and sending it to a Slack or Teams channel or a mailing list is what is left.
- Discovery for real: a collector reading LLDP-MIB and CDP-MIB, or an NMS's neighbor tables, as a `DiscoverySource`.
- The change set to the source of truth: sent to NetBox or Nautobot once there is one, each change dropped once the source has it.
- Live state from real sources: vakr first (it needs the read-only integration role its design calls for), then other monitoring tools, each as a `StateSource`. Each needs history: from the tool, or recorded by Sunstone.
- The wall display saying when no one has signed for the handover of the shift on now, as the header does, and which incidents are open.
- Incidents to and from a ticketing system (ServiceNow, Jira), once there is one: the postmortem is written, and filing it is what is left.
- Frame rates on real GPUs: run `make bench` on the hardware the NOC uses. The map and the fully expanded graphs are the ones to watch; the container's software rendering gives 6 to 12 fps zooming the map.
